### 009. 수상작 상세·앨범 지도·전역 오류 경계 정리 (2026-09-20)

- 목표: 프런트의 다음 책임 검토 대상인 수상작 상세와 앨범 지도를 화면 조율·세부 상호작용으로 분리하고, 예측하지 못한 렌더 오류를 앱 공통 화면으로 처리한다.
- 유지 계약: 수상작 상세 라우트와 목록 복귀, 즐겨찾기·비교·혼잡도·공개 비교 흐름, 앨범 지도·지역 선택·대표 기록·사진 확대·방문 기록 흐름을 바꾸지 않는다.
- 범위: API·DB·디자인을 바꾸지 않는다. 전역 오류 화면은 다시 시도와 홈 이동을 제공하며, 정상 화면 흐름에는 나타나지 않는다.
- 역할: 프런트엔드는 책임 분리와 오류 경계를 구현한다. QA는 상세·지도·오류 경로의 계약과 회귀를 검토한다.

### 007. 사진 기록 백엔드 서비스 책임 분리 (2026-09-20)

- 목표: `UserPhotoService`에 함께 있던 업로드·파일 수명·촬영일 추출과 지도 투영·지오코딩·대표 기록 관리를 유스케이스별 서비스로 분리한다.
- 유지 계약: 컨트롤러 API, DB 스키마, 사진 URL, 권한 검사, 삭제의 after-commit 파일 처리, 묶음 업로드와 수상작 비교 연동은 바꾸지 않는다.
- 역할: 백엔드는 서비스 경계와 의존성을 분리하고 기존 테스트를 보강한다. QA·보안 검토는 Controller→Service 호출, 소유권 검사, 파일 삭제 순서, 지도·묶음 조회 계약을 교차 검증한다. 통합 리드는 계약·문서·테스트를 대조한다.
- 범위 밖: 지도 좌표·외부 지오코딩 정책 변경, API DTO 변경, DB 마이그레이션은 하지 않는다.

### 008. 묶음 업로드 롤백 파일 보상 포함 (2026-09-20)

## 설계 결정

### 001. 파일 삭제는 DB 커밋 뒤에 실행 (2026-09-20)

- 결정: 사진·묶음 DB 삭제는 기존 트랜잭션에서 처리하고, 물리 파일 삭제는 Spring 트랜잭션의 `afterCommit` 단계에서만 실행한다.
- 이유: 외부 파일 저장소는 DB 롤백에 참여하지 않는다. 커밋 전에 파일을 지우면 이후 DB 롤백 시 복원된 사진 기록이 없는 파일을 가리킬 수 있다.
- 검토한 대안과 선택하지 않은 이유: 분산 트랜잭션은 로컬·S3 저장소에 일관되게 적용하기 어렵고 과도하다. 파일을 먼저 백업·복구하는 방식은 저장소별 복구 규칙이 늘어난다.
- 영향 범위: 파일 삭제 실패는 사용자 데이터 유실 대신 커밋 뒤 고아 파일로 남고 오류 로그로 관찰한다. 재시도·정리 배치는 후속 범위다.

### 002. 목록 변환 전 일괄 조회 (2026-09-20)

- 결정: 앨범 묶음의 자식 사진과 저장 수상작을 각각 ID 집합으로 한 번에 조회한 뒤, 기존 정렬 순서대로 DTO를 조립한다.
- 이유: 목록 항목 수만큼 repository를 반복 호출하던 N+1을 제거하면서 API 응답과 정렬을 유지한다.
- 영향 범위: HTTP 경로·상태 코드·DTO 형식은 바뀌지 않는다.

### 003. 비교 결과는 수정 메뉴에서 변경·삭제를 함께 관리 (2026-09-20)

- 결정: 비교 확대 팝업의 단일 `삭제` 행동을 `수정` 메뉴로 바꾸고, 사진 변경·크롭 변경·두 삭제 선택지를 함께 제공한다.
- 이유: 이미 서버에 있는 두 PATCH 계약을 실제 사용자 행동으로 연결하고, 변경과 삭제의 결과를 한곳에서 명확히 고르게 한다.
- 영향 범위: 사진 변경은 새 사진과 크롭을 동시에 저장하고, 크롭 변경은 현재 사진을 유지한다. 성공 시 팝업을 닫고 관련 목록 캐시를 갱신한다.
