## 기술 스택 (확정)

### Backend
- **Spring Boot 3.x** (Java 17+)
- **Spring Web** — REST API
- **Spring Data JPA** + Hibernate — ORM
- **Spring Security** + OAuth2 Client — 카카오 로그인
- **JWT** (jjwt 등) — 인증 토큰
- **MySQL 8.x**
- **Flyway** — DB 스키마 마이그레이션 버전관리
- **WebClient / RestClient** — 외부 API 호출
- **Caffeine 캐시** — 외부 API 응답 캐싱 (쿼터·속도 대응)

### Frontend
- **React 18 + TypeScript**
- **Vite** — 빌드 도구
- **Capacitor** — 네이티브 래핑 (Android 우선)
- 상태관리/데이터 페칭: **TanStack Query** (서버 상태 캐싱에 적합)
- 라우팅: **React Router**
- 지도: **Kakao Map JS SDK**
- 스타일: 모바일 우선 반응형 (구체 라이브러리는 08에서)

### 인프라/운영 (개발 단계)
- 이미지 저장: 개발은 로컬 디스크, 운영은 오브젝트 스토리지(S3 호환) — 07 참고
- 시크릿: `.env` / `application-local.yml` (git 제외)

## 핵심 설계 원칙

> **최우선 원칙 — 확장성 우선:** 새 기능이 추가돼도 **기존 코드 수정을 최소화**하고 확장(구현 추가)으로 대응한다. 아래 원칙들은 모두 이 목표를 위한 수단이다.

1. **도메인 모듈 경계 명확화** — 각 도메인은 독립 패키지(백엔드)/기능 폴더(프론트)로 분리. → 하네스 에이전트가 도메인 단위로 매핑됨.
2. **외부 API는 어댑터 인터페이스로 격리** — 도메인은 `XxxProvider` 인터페이스에만 의존. 외부 응답을 내부 모델로 변환하는 계층을 두어, API 변경/장애가 도메인·프론트에 전파되지 않게 함.
3. **응답 DTO 분리** — 프론트에 주는 DTO를 외부 응답/내부 엔티티와 분리. 외부 API가 바뀌어도 프론트 계약은 유지.
4. **개방-폐쇄(OCP)** — 콘텐츠 종류·외부 소스 추가는 enum 값/구현 추가로 처리하고, 기존 테이블·핵심 로직은 건드리지 않는다.

## 외부 데이터 처리 전략 (현재 결정)

- **외부 데이터(관광사진·공모전·집중률)는 DB에 저장하지 않고 실시간 호출**한다. (초기 단순화)
- 단, 위 원칙 2·3을 지켜 어댑터 인터페이스 뒤에 숨긴다 → 나중에 캐시/DB 구현으로 **교체만** 하면 전환 비용이 작다.
- 트래픽·쿼터 문제가 생기면 어댑터에 캐싱 데코레이터를 한 겹 얹는다. (도메인·프론트 변경 없음)
- 리스크 인지: 외부 API 쿼터/지연/장애에 직접 노출 — 초기 MVP 단계에서 감수.
