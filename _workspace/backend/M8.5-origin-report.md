# M8.5 backend origin configuration report

## Change scope

- `backend/src/main/resources/application.yml`
  - Changed `app.cors.allowed-origins` to explicitly read `APP_CORS_ALLOWED_ORIGINS`.
  - Preserved the five local development origins as its fallback value.
- `backend/src/test/java/com/intothepicture/global/config/CorsPropertiesTest.java`
  - Added a binding test for a comma-separated origin string into `CorsProperties.allowedOrigins` (`List<String>`).

## Decision and reason

- The deployment Compose layer can provide one comma-separated HTTPS origin without duplicating CORS configuration in source files.
- The property remains a Spring `List<String>`: Spring Boot's Binder splits the comma-separated value, so `SecurityConfig` and Kakao callback origin validation continue to consume the same list contract.
- When the environment variable is not provided, Vite, localhost HTTPS, and Capacitor local development keep their existing allowed origins.

## Verification

- `gradlew.bat test --tests com.intothepicture.global.config.CorsPropertiesTest`: passed.
- `gradlew.bat bootJar`: passed.

## Risk and follow-up

- A malformed deployed origin (wrong scheme/domain or spaces) can still deny browser CORS requests. Compose must derive the exact `https://${APP_DOMAIN}` value and QA must verify its resolved configuration.
- HTTP deployment is intentionally out of scope; its origin and cookie policy need a separate decision.
