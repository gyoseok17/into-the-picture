# M8.1 사진 묶음 백엔드 결과

작성일: 2026-08-28

## 변경 범위

- V10 마이그레이션으로 `photo_record_bundle`과 선택적 `photo_record.bundle_id` FK·인덱스를 추가했다. 기존 `photo_record`는 변경하거나 이관하지 않아 개별 사진·공모전 비교 기록을 보존한다.
- `PhotoRecordBundle` / repository와 전용 controller/service/DTO를 추가했다.
- `POST /me/photos/bundles`는 1~20장의 동일 요청 파일을 하나의 묶음과 공통 메타데이터로 저장한다.
- `GET /me/photos/bundles`는 실제 묶음과 `bundle_id IS NULL`인 기존 개별 사진을 호환 가능한 동일 DTO 배열로 반환한다.
- `DELETE /me/photos/bundles/{bundleId}`는 소유권을 서버에서 검사한다. 내부 사진 하나라도 공모전 비교에 연결되어 있으면 삭제 전 409을 반환하므로 대상은 유지된다.
- `GET /me/photos/bundles/map`은 묶음 하나당 마커 하나와 전체 내부 사진 목록을 반환한다. 기존 `/me/photos/map`은 유지했다.

## 설계 결정

- 기존 단일 사진 API와 map API를 유지해 M8.1 전환 중 비교·기존 앨범 경로가 깨지지 않게 했다.
- 새 map endpoint는 marker-level DTO를 별도로 두었다. 기존 사진은 `legacy: true`, `id: null`, 한 장짜리 marker로 표현한다.
- 파일 유효성 검사·저장·EXIF 처리의 기존 경로를 `UserPhotoService.uploadToBundle`에서 재사용했다. 다중 업로드 도중 예외가 나면 이미 저장한 파일은 보상 삭제를 시도하고 DB 트랜잭션은 롤백된다. 단일 저장 경로도 DB 저장 예외 뒤의 저장 파일을 보상 삭제하도록 보강했다.

## 검증

- `backend\\gradlew.bat test` 성공.
- `PhotoRecordBundleServiceTest`: 20장 초과 요청이 DB 생성을 시작하기 전에 거절되는지, 비교 참조가 있으면 파일·묶음 삭제를 시작하지 않는지 확인.
- `git diff --check` 성공.

## QA 보완 (2026-08-28)

- `LocalFileStorage`는 최종 파일 경로에 직접 복사하지 않고 동일 디렉터리의 임시 파일에 복사한 뒤 이동한다. 복사·이동 실패 시 임시 파일 삭제를 시도하고, 정리에 실패하면 원래 예외에 suppressed exception으로 남긴다.
- 경로 탈출 삭제는 `IOException`으로 거절한다. 서비스의 저장·삭제 보상 경로도 파일 삭제 `IOException`을 더 이상 무시하지 않는다.
- `LocalFileStorageTest`로 실패한 입력 스트림 뒤 임시 파일이 남지 않는지와 루트 밖 삭제 거절을 검증했다.

## 남은 위험 / 통합 확인

- 실제 배포 DB에 V10을 적용하는 Flyway 실행은 아직 하지 않았다. 커밋 전 QA가 migration과 프런트 multipart 필드명(`files`)·map endpoint를 교차 확인해야 한다.
