# M8.3 백엔드: 선택형 사진 저장소

## 변경 범위

- `FileStorage` 계약은 유지하고 `LocalFileStorage`와 새 `S3FileStorage`를 환경값으로 선택하도록 구성했다.
- `APP_STORAGE_TYPE`이 없거나 `local`이면 기존 서버 디스크(`./uploads`)를 사용한다.
- `APP_STORAGE_TYPE=s3`이면 AWS SDK v2 S3 클라이언트를 사용한다.
- `APP_STORAGE_TYPE`은 `local` 또는 `s3`만 허용하며, 다른 값은 명확한 설정 오류로 시작을 중단한다.
- `AWS_REGION`, `APP_STORAGE_S3_BUCKET`이 없으면 S3 빈 생성 시 명확한 설정 오류로 시작을 중단한다.

## 설계 결정

- 저장 키는 기존과 동일하게 `u/{userId}/{UUID}.{extension}`으로 생성한다. 키 생성·확장자 정규화는 `UserPhotoStorageKey` 한 곳으로 모아 Local/S3 구현의 규칙 중복을 없앴다. Multipart 원본 파일명은 신뢰하지 않으며, 확장자는 영문·숫자 1~10자만 허용하고 그 외에는 `.jpg`로 안전하게 대체한다.
- `StoredFile.url`은 S3 공개 URL이 아니라 기존 `/files/{key}` 형식을 계속 반환한다. 실제 파일 조회는 기존의 인증된 사진 API가 처리하므로 버킷을 공개하지 않는다.
- AWS 액세스 키 설정은 추가하지 않았다. AWS SDK 기본 자격 증명 체인을 사용하므로 로컬에서는 AWS CLI/프로필 자격 증명, EC2에서는 인스턴스 IAM 역할을 사용한다.
- S3 SDK 예외는 `IOException`으로 변환한다. 기존 서비스의 업로드 실패·정리 흐름과 같은 오류 경로를 유지한다.
- S3 객체 키는 `u/` 범위와 경로 안전성을 검사한다. IAM 정책의 `.../u/*` 최소 권한 범위와 맞춘다.

## 검증

- `./gradlew.bat test` 성공.
- S3 단위 테스트: 사용자별 키 형식, 비공개 애플리케이션 URL 유지, 버킷·키·콘텐츠 타입 전달, 삭제 요청, 범위 밖 키 거부, SDK 실패의 `IOException` 변환을 mock S3Client로 검증.
- 기존 LocalFileStorage 테스트도 전체 테스트에 포함해 통과.

## 위험 및 후속

- 실제 S3 업로드·조회·삭제는 로컬 AWS 자격 증명 또는 EC2 IAM 역할을 연결한 뒤 통합 검증이 필요하다.
- 현재 DB에 저장된 기존 로컬 파일은 자동 이관하지 않는다. 저장소를 S3로 바꾼 뒤 기존 파일도 계속 보여야 하면 별도 이관 계획이 필요하다.
- S3 버킷은 비공개, EC2 역할은 해당 버킷 `u/*`의 Get/Put/Delete만 허용해야 한다.

## 영향 계약

- 프런트 API, `storage_key`, 파일 조회 권한 규칙과 URL 형식은 변경하지 않는다.
