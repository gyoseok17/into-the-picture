# M8.1 단일 도메인 Compose 백엔드 보고

## 변경 범위

- `backend/docker-compose.yml`에 `frontend` 서비스가 사용할 Caddy 인증서·상태 볼륨과 외부 `80`/`443` 포트를 정의했다.
- `backend`에서 호스트 `ports`를 제거하고 Compose 내부 `expose: 8080`만 남겼다.
- `backend/.env`는 계속 backend 서비스에만 `env_file`로 주입한다. 프런트에는 `APP_DOMAIN`과 공개 `VITE_KAKAO_JS_KEY`만 전달한다.
- Docker Compose의 backend 환경에서 `APP_AUTH_REFRESH_COOKIE_SECURE=true`를 강제했다.
- `.env.example`과 README에 단일 도메인·HTTPS·공개 키·볼륨·실행 조건을 문서화했다.

## 설계 결정

- Caddy 프런트가 `/api/*`와 `/files/*`를 내부 DNS 이름 `backend:8080`으로 프록시하는 프런트 설정과 연결된다. 백엔드 포트를 공개하지 않아 우회 HTTP 접근 경로가 없다.
- `APP_DOMAIN`은 Compose 보간과 Caddy 런타임 도메인에만 전달하며, DB/JWT/REST API 시크릿은 Caddy나 프런트 빌드 컨텍스트에 전달하지 않는다.
- `VITE_KAKAO_JS_KEY`는 코드가 실제로 읽는 공개 브라우저 키 이름이다. Vite 빌드 결과에 포함되는 공개값이므로 REST 키·클라이언트 시크릿과 분리했다.
- `itp-uploads`는 현재 단일 호스트의 LocalFileStorage 보존용이며, `caddy_data`와 `caddy_config`은 HTTPS 인증서와 Caddy 상태를 보존한다.

## 검증

- 비밀값 대신 `APP_DOMAIN=example.com`, `VITE_KAKAO_JS_KEY=public-key-placeholder`를 프로세스 환경으로 제공해 `cd backend; docker compose config --quiet` 통과.
- `cd backend; .\\gradlew.bat test` 통과.
- `git diff --check` 통과.
- Docker Desktop Linux 엔진이 이 환경에서 실행 중이지 않아 이미지 빌드·실제 HTTPS 기동은 수행하지 못했다. Docker 엔진을 시작한 실제 도메인 서버에서 `docker compose up --build` 후 Caddy 인증서, `/api/v1` 프록시, Secure refresh cookie를 확인해야 한다.

## 영향과 호환성

- 로컬 HTTP 개발의 `cd backend; .\\gradlew.bat bootRun`과 프런트 Vite 개발 서버 경로는 유지된다.
- API, DB 스키마, 인증 토큰 형식은 변경하지 않았다. Secure 쿠키 강제는 Compose HTTPS 배포에만 적용된다.
