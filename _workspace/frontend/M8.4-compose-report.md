# M8.4 프런트 배포 Compose 검토 결과

## 검토 범위

- `frontend/Dockerfile`의 Vite 빌드 시점 환경값
- `frontend/Caddyfile`의 동일 출처 API·파일 프록시와 SPA fallback
- Docker Hub `gyoseok/into-the-picture-frontend:m8.3` 실행 전제

## 설계 확인

- `VITE_API_BASE=/api/v1`은 프런트 번들에 빌드되며, Caddy의 `/api/* -> backend:8080` 프록시와 일치한다.
- 업로드 파일 경로 `/files/*`도 같은 Caddy 프록시를 거치므로 브라우저는 API·파일 모두 같은 도메인으로 접근한다.
- `VITE_KAKAO_JS_KEY`는 Vite의 브라우저 공개 키로서 빌드 시점에 번들에 포함된다. 따라서 Hub의 `m8.3` 이미지에는 키가 포함되어 있고, EC2 런타임 `.env`에 다시 넣어도 번들 값은 변경되지 않는다.
- `APP_DOMAIN`은 Caddy 런타임 환경값이다. 실제 도메인을 Compose의 프런트 컨테이너에 전달하면 Caddy가 HTTP를 HTTPS로 전환하고 인증서를 관리한다.

## Docker Hub 이미지 확인

- `docker pull gyoseok/into-the-picture-frontend:m8.3` 성공
- 이미지 digest: `sha256:67253f5f48d16d71142afd380c4a3a359801f140dd91de23ee8c6ceffc19159a`
- 이미지의 정적 번들에 Kakao Maps SDK의 `appkey` URL이 포함된 것을 확인했다. 키 값은 기록하지 않았다.

## 검증

- `frontend/npm run build` 성공
- TypeScript 검사와 Vite production build 성공
- 기존 chunk size 경고(500 kB 초과)는 실패가 아니며 이번 Compose 전환으로 새로 발생한 사항이 아니다.

## 결론 및 영향 계약

- 프런트 `Dockerfile`과 `Caddyfile`의 수정은 필요 없다.
- Compose를 `image: gyoseok/into-the-picture-frontend:${APP_IMAGE_TAG}`로 전환할 때도 프런트에는 `APP_DOMAIN`만 런타임 환경값으로 전달하면 된다.
- Kakao JS 키를 변경하려면 해당 키로 프런트 이미지를 다시 빌드·태그·push해야 한다.
