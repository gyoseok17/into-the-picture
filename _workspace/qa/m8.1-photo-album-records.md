## 데이터·보안 확인

- V5에서 이관한 기존 `PhotoRecord`를 V6이 변경하지 않는다. V6은 활성/보관 목록을 위한 인덱스만 추가한다.
- 기존 `takenAt`·`placeName`·`memo`의 `null`은 허용되고, 화면은 촬영일·장소 미상과 `createdAt` 대체 정렬로 처리한다.
- `GET`, `POST`, `PATCH`, 파일 읽기, `DELETE`는 모두 `/me/**` 인증 경계와 `findByIdAndUserId` 소유자 조회를 함께 사용한다.
- JPEG EXIF는 `DateTimeOriginal`(보조 `DateTime`)만 읽고 GPS나 다른 위치 메타데이터는 조회·응답하지 않는다.
- 파일은 마지막 `PhotoRecord` 참조가 사라질 때만 기존 규칙에 따라 삭제된다. 연결된 비교 결과가 있으면 일반 삭제는 409이며, 사용자는 비교 화면에서 결과만 삭제 또는 사진까지 삭제를 선택한다.

## 발견 및 조치

1. **초기 차단 — 앨범에서 물리 삭제 경로 누락**
   - 기존 마이의 삭제 버튼이 앨범 전환 과정에서 사라져 직접 추가한 사진을 삭제할 화면 경로가 없었다.
   - 수정 창에 삭제 확인, 삭제 중 상태, 비교 연결 409 안내를 추가해 해결했다.
2. **표시 방식 연결 보완**
   - 앨범의 `PHOTO_ONLY` 상태가 비교 결과 화면에 반영되지 않았다.
   - 비교 DTO·캐시 무효화·목록·상세 렌더링을 연결해 수상작 이미지를 실제로 숨기도록 해결했다.

## 자동 검증

- `backend/.\\gradlew.bat test` 통과. JPEG EXIF 촬영 시각/EXIF 없음, PATCH의 필드 누락과 명시적 `null` 구분 테스트를 포함한다.
- `frontend/npm run build`, `git diff --check` 통과.
- 기존 Vite 500KB 번들 크기 경고만 남아 있으며 이번 변경의 차단 이슈는 아니다.

## 수동 통합 확인 권고

1. JPEG를 날짜 없이 추가해 EXIF 촬영일이 채워지는지, PNG/WebP·EXIF 없는 JPEG가 `촬영일 미상`으로 남는지 확인한다.
2. 날짜·장소·메모를 채운 뒤 비우고 저장해 `null` 표시와 시간/장소 정렬 폴백을 확인한다.
3. 보관 → 비교 사진 고르기에서 제외 → 보관함에서 꺼내기 → 다시 선택 가능 순서를 확인한다.
4. 비교 사진을 `내 사진만 보기`로 바꿔 비교 목록·상세에서 수상작 이미지가 숨겨지는지 확인한다.
5. 일반 사진 삭제와 비교 연결 사진 삭제 409 안내, 비교 화면의 결과만 삭제/사진도 삭제 선택을 확인한다.
6. 다른 로그인 사용자로 기록 URL·파일 URL·PATCH·DELETE를 요청해 404/권한 차단을 확인한다.
