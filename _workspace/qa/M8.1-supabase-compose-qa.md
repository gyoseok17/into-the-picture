# M8.1 Supabase 외부 DB Compose 전환 QA·보안 검토

## 판정

조건부 통과 — 구성·보안 계약과 JAR 빌드는 통과했다. Docker Desktop 엔진이 꺼져 있어 실제 이미지 빌드·컨테이너 기동은 이 환경에서 확인하지 못했다.

## 사전 위험과 해소

- 과거 `docker-compose.yml`은 하드코딩된 MySQL 8 개발 비밀번호와 DB 컨테이너를 사용했다. 현재 Compose는 해당 서비스를 제거하고 Supabase PostgreSQL을 외부 환경변수로 직접 사용한다.
- 처음에는 `spring.config.import`가 필수 `file:.env[.properties]`여서, `.env`를 이미지에서 제외하면 컨테이너가 기동 전 실패할 위험이 있었다. `optional:file:.env[.properties]`로 전환해 Gradle 로컬 실행은 `backend/.env`를 계속 읽고, Compose·운영은 프로세스 환경변수만으로 기동할 수 있게 했다.

## 교차 검토

- `backend/docker-compose.yml`: backend 서비스 하나만 정의하며 `env_file: .env`로 DB·JWT·외부 API 시크릿을 주입한다. PostgreSQL/Supabase 연결 정보는 Spring `DB_HOST`·`DB_PORT`·`DB_NAME`·`DB_USERNAME`·`DB_PASSWORD` 계약과 일치한다.
- `backend/Dockerfile`과 `.dockerignore`: `.env`, 빌드 산출물, 로컬 업로드를 빌드 컨텍스트에서 제외한다. 이미지에는 JAR만 복사하며 시크릿을 `COPY`·`ARG`·`ENV`로 넣지 않는다. 비루트 `appuser`로 실행한다.
- 로컬 파일 업로드: Compose가 `APP_STORAGE_LOCAL_DIR=/app/uploads`와 named volume `itp-uploads`를 연결한다. `LocalFileStorage`의 환경변수 바인딩과 경로가 맞고, 컨테이너 재생성 뒤에도 같은 Docker 호스트에서는 보존된다.
- 로컬 실행 보존: `./gradlew bootRun`은 `backend/.env`를 읽는 기존 경로를 유지한다. README에 Gradle 및 Docker 실행을 분리해 안내한다.
- 레거시 MySQL·3306·하드코딩 DB 시크릿 참조는 backend 범위에서 남아 있지 않다.

## 배포 제한 (필수 고지)

S3 또는 Supabase Storage는 아직 구현되지 않았다. 따라서 `itp-uploads`는 한 Docker 호스트의 로컬 볼륨일 뿐이며, 서버 손실·다중 인스턴스·다른 호스트 배포 시 사용자 사진을 보장하지 못한다. 현재 Compose는 단일 서버의 임시 운영 방식으로만 사용해야 하며, 다중 서버·영속 배포 전에는 객체 스토리지 전환이 필요하다.

## 검증

- `./gradlew.bat bootJar` 통과 — Dockerfile의 JAR 산출물 전제 확인
- Compose YAML·`env_file`·volume 구성을 정적 검토
- `docker compose build backend`는 Docker Desktop Linux 엔진 파이프가 없어 실행 불가 (`//./pipe/dockerDesktopLinuxEngine` 없음). 코드·Compose 오류가 아니라 로컬 Docker 엔진 미기동 상태다.

## 권고

- Docker Desktop을 켠 뒤 `docker compose build`와 실제 Supabase 연결·Flyway·업로드 후 컨테이너 재생성 테스트를 한 번 수행한다.
- 운영 배포 전에는 객체 스토리지 전환과 백업·복구 정책을 별도 마일스톤으로 확정한다.
