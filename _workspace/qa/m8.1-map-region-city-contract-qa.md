# M8.1 앨범 지도 권역·시 선택 QA/계약 검토

작성일: 2026-08-26
범위: 사진 기록 업로드·수정·지도 조회에 사용자가 선택한 지도 권역과 대략적 시를 저장하는 후속 변경. 프로덕션 코드 변경 없음.

## 현재 기준선

- `photo_record`는 자유 입력 `place_name`과 외부 지오코딩 결과인 `latitude`, `longitude`, `geocode_checked_at`만 가진다.
- `POST /me/photos`는 multipart의 `takenAt`, `placeName`, `memo`를 받고, `PATCH /me/photos/{id}`는 누락과 명시적 `null`을 구분한다.
- `GET /me/photos/map`은 활성 기록만 대상으로, 좌표가 없는 `placeName`을 최대 20개씩 지오코딩한 뒤 좌표가 있는 기록만 반환한다.
- 따라서 현재의 지도 좌표는 장소명 검색 결과이며, 사용자가 지도에서 고르는 "8개 블록/시" 정보는 저장되지 않는다.

## 권장 최소 데이터 모델

지도 그림의 8개 블록은 법정 시·도 경계와 일치하지 않는다. DB 이름을 `sido`/`sigungu`로 두면 실제 행정구역이라고 오해하고, 광역시·군을 억지로 넣게 된다. 지도 전용 값으로 분리한다.

| 필드 | 저장값 | 규칙 |
| --- | --- | --- |
| `map_region_code` | 지도 그림의 8개 큰 블록을 가리키는 안정적 코드 | nullable. 예: 사람이 읽는 이름이 아닌 고정 코드 |
| `map_city_code` | 해당 블록 안에서 고른 대략적 시/도시권의 안정적 코드 | nullable. 선택하면 반드시 `map_region_code`에도 속해야 함 |

- 화면에 보이는 한국어 이름과 핀 좌표는 코드에서 파생한다. 이름을 DB에 중복 저장하지 않는다.
- `placeName`은 계속 자유 입력 장소명이고, 지도 선택값과 별개다. 서로 자동 덮어쓰지 않는다.
- `latitude`/`longitude`에는 장소 지오코딩의 실제 검색 좌표만 보관한다. 선택한 시의 대표 좌표를 이 칼럼에 써 넣으면 정확 좌표와 대략 좌표를 구별할 수 없어 향후 공유·정확도 표시가 깨진다.

## API 계약 제안

### 생성·수정

- `POST /me/photos` multipart에 선택 필드 `mapRegionCode`, `mapCityCode`를 추가한다.
- `PATCH /me/photos/{id}`에 같은 필드를 추가하고, 기존 `placeName`처럼 누락과 명시적 `null`/빈 문자열을 구분한다.
- 서버의 `MapLocationCatalog`가 코드 존재 여부와 `도시 -> 권역` 소속을 검증한다. 클라이언트 검증만으로 처리하지 않는다.
- 도시를 보낼 때 권역이 없거나 다른 권역이면 `400 INVALID_REQUEST`; 도시를 지우면 권역만 남기는 것은 허용한다. 권역을 지우는 요청은 도시도 함께 지워야 한다.

### 응답·지도

- 일반 사진 DTO와 map DTO에 `mapRegionCode`, `mapCityCode`를 추가한다. 기존 소비자는 새 필드를 무시할 수 있어 응답 확장은 호환된다.
- 지도 DTO는 좌표가 없는 기록을 그대로 내보내지 않는다. 지도 조회는 `(정확 좌표 있음) OR (mapCityCode 있음)` 기록을 반환하며, 전자는 장소 좌표를, 후자는 서버 카탈로그의 도시 앵커 좌표를 `lat`/`lng`에 채운다. `locationSource: PLACE | CITY`로 두 경우를 구분한다.
- 프런트 지도는 반환된 좌표만 쓰되 `locationSource`로 대략적 도시 표시임을 구분할 수 있다. 둘 다 없으면 기존처럼 지도에서 제외한다.
- `GET /me/photos/map/locations`는 권역 코드·표시명과 그 안의 도시 코드·표시명을 반환해 프런트 선택지가 서버 검증 카탈로그와 어긋나지 않게 한다.
- 선택한 지역이 있더라도 지도 조회에서 매번 외부 지오코딩을 하지 않도록, `needsGeocoding`은 `mapCityCode`가 있으면 false로 처리하는 것이 비용·속도 면에서 적절하다. 정확한 장소 핀이 필요하다는 별도 사용자 동작이 생길 때만 다시 지오코딩한다.

## 마이그레이션·기존 데이터 호환성

1. 다음 순번의 Flyway 마이그레이션에 nullable `map_region_code VARCHAR(...)`, `map_city_code VARCHAR(...)`를 추가한다. 기존 V5~V7 파일을 수정하지 않는다.
2. 기존 모든 기록은 두 값이 `NULL`인 유효 기록으로 보존한다. 일괄 역지오코딩/자동 분류를 하지 않는다. 잘못 분류된 지역이 개인 여행 기록에 남는 위험이 더 크다.
3. 기존 `latitude`/`longitude`와 지오코딩 재시도 시각을 건드리지 않는다. 새 코드가 없는 레코드는 현재 지도 동작을 그대로 유지한다.
4. 지도 조회 조건이 바뀌므로 `(user_id, archived_at, map_city_code)` 인덱스를 추가할지 실행 계획과 데이터량을 확인한다. 현재 개인 앨범 규모라 필수는 아니나, 조회 조건에 직접 쓰면 추가하는 편이 일관된다.

## 구현 전 결정이 필요한 한 가지

"시" 목록은 실제 전국 행정 `시`만 쓸지, 군·광역시도 지도에서 보이는 도시권으로 포함할지 확정해야 한다. 여행지는 군에 많은 만큼 실제 `시`만 두면 선택할 수 없는 사진이 많다. 권장안은 **지도용 도시권 목록**(시, 군, 광역시를 모두 포함 가능)으로 두되 UI 문구는 "도시/지역"으로 표시하는 것이다. 이는 지도 그림의 대략 표기와도 맞는다.

## QA 체크리스트

- [ ] 비로그인 생성·수정·지도 조회가 모두 401이며, 다른 사용자의 recordId로 PATCH/파일/지도 데이터를 우회할 수 없다.
- [ ] 유효한 권역만, 그리고 해당 권역에 소속된 도시만 저장된다. 임의 코드·불일치 조합은 400이다.
- [ ] PATCH에서 필드 누락은 유지, 명시적 삭제는 삭제, 권역 삭제와 도시 잔존은 거절 또는 함께 삭제라는 계약대로 동작한다.
- [ ] 단일 업로드·20장 일괄 업로드 모두 공통 선택 지역이 동일하게 저장되고, 일부 실패 재시도에서 중복 생성되지 않는다.
- [ ] 기존 레코드(`map*` null)는 목록·수정·보관함·비교 연결·기존 지오코딩 지도 핀을 회귀 없이 유지한다.
- [ ] 장소명이 있고 지역 선택이 없는 사진은 기존 지오코딩 핀, 장소명이 비어도 도시 선택이 있는 사진은 도시 앵커 핀, 둘 다 없는 사진은 안내 수에만 포함된다.
- [ ] 장소명 수정이 선택 도시를 지우지 않고, 지역 수정이 기존 정확 좌표를 임의로 덮어쓰지 않는다.
- [ ] 모바일/PC에서 8개 지도 블록의 클릭 영역과 도시 선택지가 같은 코드 체계를 사용하며, 선택 강조·저장 후 재진입·핀 위치가 일치한다.

## 판정

권역/도시 선택을 별도 코드로 저장하고, 기존 자유 장소명 지오코딩과 혼합하지 않으면 최소 변경으로 정확도·비용·향후 지역 필터 확장성을 함께 확보할 수 있다. API와 DB를 바꾸는 기능이므로 백엔드·프런트엔드·통합 QA의 병렬 구현과 계약 문서 갱신이 필요하다.
