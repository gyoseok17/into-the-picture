# M8.1 지도 위치 대표 기록 통합 QA

작성일: 2026-08-29
기준 계약: `_workspace/contracts/M8.1-map-location-representative.md`
상태: 구현 전 계약·회귀 위험 검토 완료, 최종 구현 대조 대기

## 검증 대상과 불변 조건

- 대표 설정은 `사용자 + 서버가 계산한 위치 키`마다 최대 하나다. 클라이언트가 위치 키나 사용자 ID를 요청으로 넘겨 대표 범위를 바꾸지 않는다.
- 권역·시군 사진은 `CITY:{mapRegionCode}:{mapCityCode}`, 기존 좌표 사진은 소수 셋째 자리로 정규화한 `PLACE:{lat}:{lng}`을 서버에서 계산한다.
- 대표가 없는 위치는 기존처럼 최신 방문 기록을 표시한다. 대표 설정은 정렬 규칙이나 사진·방문 묶음 자체를 변경하지 않는다.
- 대표 대상 사진 기록을 삭제해도 다른 사진·묶음·파일은 삭제되지 않는다. 참조만 `NULL`이 되고 지도는 최신 기록으로 안전하게 대체한다.

## API · DTO 계약 점검

### PUT `/api/v1/me/photos/map/representative`

| 시나리오 | 기대 결과 | 차단 여부 |
| --- | --- | --- |
| 인증된 사용자가 자기 사진 기록 ID 지정 | `204 No Content`, 해당 위치의 대표만 교체 | 차단 |
| 비로그인 | 프로젝트 표준 인증 오류(401), 설정 변화 없음 | 차단 |
| 다른 사용자의 사진 기록 ID | 존재 여부를 노출하지 않는 표준 권한/없음 오류, 설정 변화 없음 | 차단 |
| 없는 사진 기록 ID | 404 또는 표준 없음 오류, 설정 변화 없음 | 차단 |
| 지도 위치가 없는 사진 기록 | 400, 대표 설정을 만들지 않음 | 차단 |
| 같은 대표를 재지정 | 204, 중복 preference 행 없음 | 차단 |
| 같은 위치의 다른 방문 기록 지정 | 기존 행을 갱신하고 `(user_id, location_key)`는 한 행 유지 | 차단 |

`photoRecordId`는 숫자 하나만 허용하며, 요청 body의 위치 키·사용자 ID·사진 URL 등 신뢰할 수 없는 범위 지정 값은 받지 않는다. 오류 응답은 기존 공통 오류 DTO 형식과 일치해야 한다.

### GET `/api/v1/me/photos/bundles/map`

- 각 방문 기록 DTO에 `representative: boolean`이 포함되어야 한다. 프런트 `PhotoRecordBundleMapPin` 타입과 필드 이름·nullability를 동일하게 맞춘다.
- 같은 위치 그룹은 대표가 지정됐을 때 정확히 한 건만 `true`다. 설정이 없거나 대표 record가 삭제되어 참조가 `NULL`이면 최신 방문 기록 한 건이 `true`다.
- 서로 다른 사용자, 서로 다른 위치의 대표 상태가 섞이지 않는다.
- 사진 수가 아니라 방문 기록(묶음 또는 legacy 단일 기록) 수가 마커 개수 계산의 기준이다.

## DB · 삭제 안전성

- preference 테이블은 `UNIQUE(user_id, location_key)` 제약을 둬 동시 요청에도 위치당 대표가 둘 생기지 않게 한다.
- `representative_photo_record_id`는 nullable FK이며 `ON DELETE SET NULL`이다. 사진 기록 삭제 시 preference 행을 삭제하거나 다른 기록을 지우면 안 된다.
- FK 대상 record와 preference의 `user_id` 일치를 DB FK만으로 강제할 수 없으므로, 대표 지정 서비스가 record를 반드시 `id + user_id`로 조회·검증한다.
- migration은 기존 `photo_record`, `photo_record_bundle`, `user_photo` 행을 수정하거나 삭제하지 않는다. 기존 사진은 대표 미설정 상태에서 기존 최신 선택 규칙을 유지한다.
- 대표가 속한 묶음을 삭제할 때도 FK가 null 처리되는지, 비교 참조로 bundle 삭제가 409인 경우 preference가 변하지 않는지 확인한다.

## 지도 렌더링 시나리오

1. 같은 시군에 A(과거), B(최근) 두 묶음을 만든다. 기본 지도 메인은 B이고 B만 대표 표시다.
2. A를 대표로 설정한 뒤 map API를 다시 조회한다. A가 대표이며 지도 카드 메인도 A로 바뀐다. 마커 수는 여전히 방문 기록 2건이다.
3. A를 삭제한다. map API에는 B가 대표로 표시되고, A의 preference 참조는 null이다.
4. A가 포함된 bundle 삭제가 비교 참조 409으로 막히면, A는 계속 대표이며 지도 메인도 바뀌지 않는다.
5. 권역·시군 미지정 사진을 좌표 위치로 대표 지정한다. 동일한 소수 셋째 자리 좌표 사진만 같은 위치로 처리하며, 인접하지만 다른 좌표는 합치지 않는다.
6. 대표가 없는 기존 legacy 단일 사진, 새 묶음 사진, 보관함 사진을 함께 둔다. active map에는 활성 사진만 나오고 보관함 전환·삭제 후 대표 fallback이 일관되게 계산된다.
7. 모바일과 PC에서 `이곳의 기록 N개 보기`를 열고 대표 설정 후 목록이 닫히며, 메인 카드만 교체된다. 방문 목록이 카드 본문 높이를 계속 키우지 않는다.

## 지도 카드와 별도 기록 내역 시트 UX 계약

### 고정 본문

- 지도에서 마커를 고르면 본문에는 **현재 대표 기록 하나**만 표시한다. 대표가 없을 때만 최신 기록을 임시 대표로 쓴다.
- 본문 하단에는 다른 기록이 있을 때만 `이곳의 기록 N건 보기` 한 줄을 둔다. `N`은 현재 대표를 포함한 해당 위치의 전체 방문 기록 수다.
- 대표가 아닌 기록의 썸네일·날짜 목록을 본문에 미리 나열하거나, `전체 보기`로 본문 높이를 늘리지 않는다. 방문 횟수가 늘어도 지도 카드의 높이는 유지되어야 한다.
- 기록이 하나면 이 줄과 내역 진입점은 숨긴다.

### 별도 내역 시트

- `이곳의 기록 N건 보기`를 누르면 현재 지도 카드 위에 별도 내역 레이어를 연다. 모바일은 하단 시트, PC는 지도 카드와 충돌하지 않는 모달/팝오버여야 하며 배경을 눌러 닫을 수 있다.
- 시트는 위치명, 전체 기록 수, 각 기록의 대표 사진·방문일·사진 수를 보여 준다. 현재 대표은 명확하게 표시한다.
- 시트에서 다른 기록을 `대표로 설정`하면 PUT 성공 뒤 목록을 자동으로 닫고, 지도 메인만 새 대표로 교체한다. 마커 위치·마커 수·현재 지도 확대 상태는 유지한다.
- 네트워크 실패 시 시트를 닫거나 현재 대표 표시를 낙관적으로 바꾸지 않는다. 오류와 재시도 가능한 `대표로 설정` 동작을 유지한다.
- 시트가 열린 상태에서 필터 변경, 마커 닫기, 사진/묶음 삭제, map query 재조회가 일어나면 대상 위치·기록이 여전히 존재하는지 확인한다. 사라졌으면 시트를 닫고 포커스를 안전하게 해제한다.

| 같은 위치에 2건 | 대표 카드 + `이곳의 기록 2건 보기`; 시트에는 두 기록 모두 표시 |

| 모바일 뒤로가기/ESC/배경 클릭 | 시트만 닫히고 지도 마커와 대표 카드 상태는 유지 |

## 현재/예정 UI 대조 (2026-08-29)

- 현재 `VisitHistory`는 `isHistoryOpen`으로 카드 본문 안에 여러 이전 기록을 펼친다. 이는 "한 줄 + 별도 내역 시트" 요구와 다르므로, 최종 UI에서는 대체 경로를 제거해야 한다.
- 현재 본문 카피 `이전 방문 기록`은 대표를 바꿀 수 있는 전체 목록의 의미와 맞지 않는다. 최종 노출 이름은 `이곳의 기록 N건 보기`로 통일한다.
- 대표 설정 훅의 성공 후 캐시 무효화와 시트 닫기 책임을 분리한다. API 훅은 map 데이터 갱신, 화면 컴포넌트는 시트 닫기와 포커스/선택 상태만 책임진다.

## 기록 전환 사진 인덱스 안전성 (2026-08-29)

### 원인

- `MapFocus`는 `photoIndex` 상태를 가진 채 다른 방문 기록으로 `recordIndex`만 바꾼다.
- 기존 `useEffect`에서 `record.id` 변경 뒤 `setPhotoIndex(0)`을 호출해도 effect는 **새 렌더가 화면에 반영된 뒤** 실행된다.
- 따라서 다장 기록에서 마지막 사진(`photoIndex = 2`)을 보고 한 장짜리 기록으로 전환하면, 한 번의 렌더 동안 `record.photos[2]`가 `undefined`다. 이어지는 `photo.url`, `photo.originalFilename` 접근이 런타임 오류를 낼 수 있다.

### 수정 계약

- 표시 전에 `safePhotoIndex = min(photoIndex, record.photos.length - 1)`처럼 범위를 동기적으로 보정하거나, 기록 ID를 가진 사진 뷰어를 별도 key로 재마운트해 새 기록마다 인덱스 0을 보장한다.
- 이전/다음 사진 이동, 썸네일 선택, 사진 수 표시는 모두 같은 안전 인덱스를 기준으로 동작해야 한다.
- 빈 `photos` 배열은 기존처럼 카드/시트를 렌더하지 않고 안전하게 종료한다. API 계약상 정상 map pin은 최소 한 장이지만, 깨진 데이터가 화면 전체를 중단시키면 안 된다.

### 필수 회귀 시나리오

| 전환 | 준비 | 기대 결과 |
| --- | --- | --- |
| 다장 → 한 장 | A(3장)의 3번째 사진을 본 뒤 B(1장)를 선택 | 오류 없이 B 첫 사진, 사진 `1/1` 표기·캐러셀·썸네일은 없음 |
| 다장 → 다장(더 적은 수) | A(5장)의 5번째에서 B(2장) 선택 | B 첫 사진 또는 범위 내 사진만 표시, `3/2` 같은 표기 없음 |
| 한 장 → 다장 | A(1장)에서 B(3장) 선택 | B 첫 사진과 `1/3`, 양쪽 이동·썸네일 동작 |
| 다장 내부 순환 | 2장/3장 기록 각각 이전·다음 반복 | 인덱스가 음수·사진 수 이상이 되지 않고 순환 |
| 대표 시트에서 기록 선택 | 대표/비대표를 포함한 서로 다른 사진 수의 항목 선택 | 시트가 닫힌 뒤 지도 메인이 안전 인덱스 0으로 전환; 대표 상태와 사진 인덱스가 섞이지 않음 |
| 대표 설정 성공 뒤 map 재조회 | 현재 3번째 사진을 보는 중 다른 기록을 대표로 설정 | 시트 닫힘·새 대표 메인 첫 사진, 이전 `photoIndex`가 재사용되지 않음 |
| 대표 설정 실패 | 시트에서 PUT 실패 | 시트·선택 기록·사진 인덱스 유지, 메인과 대표 표시는 바뀌지 않음 |
| 삭제/필터 재조회 | 열려 있던 기록이 map 응답에서 사라짐 | 카드/시트가 안전하게 닫히고 undefined 사진 접근 없음 |

이 범위 오류로 지도 카드가 렌더 중단되면 **차단**이다. 다장→한장, 시트에서의 기록 선택, 대표 지정 후 map 갱신은 수동 QA와 컴포넌트 테스트 중 적어도 하나로 확인해야 한다.

## 메인 MapFocus 헤더의 대표 상태 UI (2026-08-29)

### 표시 계약

- 대표 상태는 지도 메인 카드의 **헤더 영역**에서만 compact badge/button으로 표시한다.
  - 현재 대표: `대표 기록` badge
  - 대표 아님: `대표로 설정` 버튼
- 설명 문장과 대표 설정 버튼을 별도 행으로 두지 않는다. 사진 아래에 대표 안내 행이 남으면 카드 높이가 불필요하게 늘어나므로 최종 구현에서 제거한다.
- 헤더는 장소명·방문일·닫기 버튼과 좁은 모바일 폭에서도 겹치지 않아야 한다. 장소명이 긴 경우 제목을 우선 truncate하고 대표 badge/button은 눌릴 수 있는 최소 크기를 유지한다.
- 기록이 하나뿐이어도 대표 badge는 보여 줄 수 있으나, 대표 변경 버튼과 `이곳의 기록 N건 보기`는 보이지 않는다.

### 상태 전환·mutation 실패 시나리오

| 상황 | 기대 결과 |
| --- | --- |
| 마커 최초 선택 | map 응답의 `representative`가 true인 기록이 메인에 열리고 헤더 badge 표시 |
| 대표 아님 기록을 내역 시트에서 선택 | 시트가 닫히고 해당 기록을 메인에서 볼 수 있다면 헤더에 `대표로 설정`만 표시; 이전 대표 badge가 남지 않음 |
| 메인에서 대표로 설정 성공 | 중복 클릭은 pending 동안 막고, 성공 후 cache 재조회 기준으로 대표 badge 표시. 별도 설명 행을 만들지 않음 |
| 내역 시트에서 대표로 설정 성공 | 시트 닫힘, 새 대표 기록이 메인, 헤더 badge 표시. 이전 대표는 다음 map 응답에서 버튼 상태 |
| PUT 실패(401/403/400/409/500/네트워크) | 메인·시트는 열린 상태 유지, 기존 badge/button 상태 유지, 버튼 재활성화 및 오류 안내. optimistic badge 전환 금지 |
| 실패 뒤 재시도 | 같은 버튼으로 1회 요청만 보내며 성공 뒤에만 badge 전환 |
| map 재조회 지연/실패 | 로컬 state만 true로 고정해 다른 기록과 두 badge가 되지 않는다. 최신 map 데이터가 오기 전에도 대표 변경 UI를 일관되게 제한하거나 명확한 갱신 상태를 보임 |
| 대표 record 삭제·필터 전환 | 사라진 record의 badge/button이 남지 않고 fallback 대표 또는 포커스 해제 상태로 전환 |

### 접근성·반응형 점검

- badge는 상태 텍스트를 그대로 제공하고, 버튼은 `대표로 설정`이라는 접근 가능한 이름·disabled/pending 상태를 가진다.
- 헤더의 대표 버튼, 닫기 버튼, 사진 이동 버튼의 탭 순서가 논리적이며, 내역 시트가 열리면 포커스가 시트로 이동하고 닫히면 원래의 `이곳의 기록 N건 보기`로 복귀한다.
- 모바일 320px 폭과 PC에서 헤더가 두 줄이 되더라도 카드 바깥으로 밀리거나 사진 영역을 덮지 않는지 확인한다.

## 현재 코드와의 사전 대조 (2026-08-29)

- 현재 `PhotoRecordBundleMapPinDto`와 프런트 `PhotoRecordBundleMapPin`에는 아직 `representative` 필드가 없다. 구현 시 백엔드 DTO·map API·프런트 타입을 함께 바꾸지 않으면 계약 불일치다.

- 아직 preference migration/엔티티/권한 검증 경로가 확인되지 않았다. 구현 반영 후 아래 최종 게이트를 재검증한다.

## 판정 기준

대표가 다른 사용자의 기록에 설정되거나, 위치 없는 기록에 설정되거나, 삭제 후 지도 조회가 깨지거나, 두 대표가 동시에 나오는 경우는 **차단**이다. 대표 미지정 상태의 최신 기록 선택, 지도 카드의 고정 높이, 목록 열기/닫기 같은 표현 문제는 기능을 막지는 않지만 사용자 확인 전 권고로 남긴다.
