# M8.1 이미지 4형식 통합 QA 계획

작성일: 2026-08-26
상태: 통합 검토 완료 — 수동 실물 파일 확인 권고

## 대상 계약

- 업로드 대상은 JPEG, PNG, WebP, HEIC/HEIF 네 형식이다.
- 기존 JPEG·PNG·WebP 업로드 및 비교 사진 흐름은 호환되어야 한다.
- 서버는 파일명이나 브라우저가 보낸 MIME만 신뢰하지 않고, 허용 형식과 실제 파일 시그니처를 함께 확인한다.
- 10MB 제한, 로그인 사용자 소유권, 비공개 파일 조회 규칙은 기존과 동일하다.
- 촬영일은 사용자가 직접 입력한 값이 최우선이다. 자동 추출을 못 해도 업로드를 막지 않고 빈 값 또는 수동 입력으로 진행할 수 있어야 한다.

## 사전 확인 기준

| 경계 | 확인 항목 | 통과 기준 |
| --- | --- | --- |
| 프런트 선택 | `accept`와 안내 문구 | JPEG, PNG, WebP, HEIC, HEIF를 선택할 수 있고 제한 안내가 실제 서버 계약과 일치한다. |
| 업로드 요청 | FormData/필드 | 파일·촬영일·장소·메모 계약이 기존 API와 호환되며, 형식 확장 때문에 필드가 누락되지 않는다. |
| 서버 MIME | 허용 MIME 정규화 | `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif` 및 브라우저·기기별 동등 MIME 처리 여부가 명시돼 있다. 빈/알 수 없는 MIME은 이름만으로 허용하지 않는다. |
| 서버 시그니처 | 실제 파일 검사 | JPEG SOI, PNG 서명, WebP RIFF/WEBP 및 HEIF/HEIC ISO-BMFF `ftyp` 브랜드를 확인한다. MIME-시그니처 불일치는 거부한다. |
| 저장·응답 | `contentType`/파일명/크기 | 실제 검증된 MIME만 저장·응답하며 기존 사진·비교 레코드를 깨지 않는다. |
| 파일 제공 | 다운로드 응답 | 인증·소유권 확인 후 올바른 `Content-Type`으로 제공하고, 다른 사용자는 접근할 수 없다. |

## 촬영일과 미리보기 검토

- JPEG EXIF 자동 촬영일 채우기는 계속 동작해야 한다.
- PNG/WebP/HEIC/HEIF는 메타데이터 지원 범위를 명확히 한다. 추출 미지원·메타데이터 없음·파싱 실패는 오류가 아니라 `촬영일 미상` 또는 수동 입력 가능 상태여야 한다.
- 직접 입력한 촬영일은 자동 추출 결과로 덮어쓰지 않는다.
- 선택 직후 미리보기는 브라우저가 지원하는 형식에서 표시된다. HEIC/HEIF를 현재 브라우저가 디코딩하지 못하면 업로드 전·후 모두 깨진 이미지 대신 형식 지원 안내와 파일명/수동 촬영일 입력을 제공해야 한다.
- 서버가 HEIC/HEIF를 저장만 하고 브라우저에서 렌더링하지 못하는 경우, 앨범·비교 화면에서 빈 카드 또는 무한 로딩이 없어야 한다. 변환을 도입한다면 원본 보존, 변환 실패, 표시용 파일 MIME 계약을 별도 확인한다.

## 보안·오류·회귀 QA

- 위장 확장자, 허용 MIME을 가장한 비이미지, 잘린 파일, 10MB 초과, 0바이트 파일을 각각 거부한다.
- HEIC/HEIF의 여러 `ftyp` 브랜드(예: `heic`, `heix`, `hevc`, `hevx`, `mif1`, `msf1`) 중 지원 범위와 거부 범위를 테스트 또는 코드로 명시한다.
- 업로드 실패는 사용자에게 재선택 또는 수동 촬영일 입력 같은 다음 행동이 보이는 메시지여야 한다.
- JPEG·PNG·WebP의 업로드 → 내 앨범 표시 → 비교 선택 → 비교 저장/교체 → 개인 사진 삭제 흐름을 회귀 확인한다.
- HEIC/HEIF도 지원 브라우저에서 위 흐름을 확인하고, 미지원 브라우저에서는 저장·목록·삭제가 안전하며 미리보기 실패가 페이지를 깨지 않는지 확인한다.
- 기존 파일 경로, `UserPhotoDto`/`PhotoRecord` API, 정렬의 `takenAt ?? createdAt` 규칙이 유지되는지 교차 확인한다.

1. 백엔드 변경 파일, 허용 MIME/시그니처 정책, 단위·통합 테스트 결과
2. 프런트 변경 파일, 선택·미리보기·촬영일 폴백 동작과 빌드 결과
3. 네 형식별 실제 업로드 결과와 실패 케이스의 HTTP 상태·사용자 메시지
4. 기존 JPEG·PNG·WebP 비교 기능 회귀 결과

## 통합 검토 결과 (2026-08-26)

### 생산자·소비자 계약 대조

- 프런트 파일 선택은 `image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif`와 `.heic`, `.heif`를 허용한다.
- 서버 `ImageUploadValidator`는 요청 MIME과 매직 바이트를 함께 검증한다. JPEG SOI, PNG 서명, WebP RIFF/WEBP, HEIC/HEIF ISO-BMFF `ftyp`와 HEIF 브랜드를 확인한다. AVIF는 명시적으로 거부한다.
- 저장 및 파일 응답은 검증된 MIME을 사용한다. HEIC와 HEIF는 각각의 요청 MIME을 유지하므로 브라우저의 파일 제공 판단과 일치한다.
- 촬영일은 요청값 우선이며, 없을 때만 서버가 `DateTimeOriginal` 후 `DateTime`을 시도한다. 실패·미지원은 `null`로 폴백한다. 프런트는 JPEG·PNG·WebP EXIF를 사전 채우고, HEIC/HEIF는 수동 입력 안내로 안전하게 처리한다.
- 미리보기 디코딩이 실패하면 파일명과 업로드 동작을 남긴 채 안내를 표시한다. HEIC/HEIF 미지원 브라우저에서 빈 이미지로 화면이 깨지지 않는다.

### 자동 검증

- `backend/gradlew.bat test` 통과: 형식별 MIME·시그니처, MIME/시그니처 불일치와 AVIF 거부, 메타데이터 null 폴백을 포함한다.
- `frontend/npm run build` 통과.
- `git diff --check` 통과. LF/CRLF 변환 경고만 있으며 공백 오류는 없다.
- 기존 비교 API와 개인 사진 파일 경로·인증 규칙은 변경하지 않았다.

### 권고 및 수동 확인

1. 실제 iPhone HEIC와 EXIF를 포함한 PNG/WebP를 업로드해 기기별 MIME, 미리보기, 촬영일 결과를 확인한다.
2. HEIC/HEIF를 렌더링하지 못하는 브라우저에서 앨범 카드·편집 화면·비교 선택이 안내 상태로 안전한지 확인한다.
3. 업로드 패널의 `JPEG 사진을 고르면` 안내 문구는 JPEG 외 PNG/WebP의 자동 촬영일 추출도 지원하므로 `사진 정보를 읽을 수 있으면`처럼 넓게 정리하는 것을 권고한다. 동작 차단 이슈는 아니다.

### 차단 이슈: 비교 화면 직접 업로드 (2026-08-26)

- 발견: `ComparePage`의 `사진 고르기 > 추가하기` 입력이 처음에는 JPEG·PNG·WebP만 허용했다.
- 조치 완료: 비교 화면의 직접 업로드·사진 교체 입력도 JPEG·PNG·WebP·HEIC/HEIF 및 확장자를 허용하도록 맞췄다. 업로드 오류 안내도 4형식·10MB 계약으로 갱신됐다.
- 재검토: 비교 화면의 미리보기와 저장 후 개인 파일 표시는 공통 `ImageSource`의 이미지 오류 폴백을 사용하므로, 브라우저가 HEIC/HEIF를 디코딩하지 못해도 빈 화면 대신 안내 상태가 표시된다.
