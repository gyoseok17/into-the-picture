# M8.1 단일 도메인 Compose 배포 QA·보안 검토

## 판정

조건부 통과 — Compose 구성·프런트/백엔드 빌드·보안 경계는 통과했다. Docker Desktop 엔진이 꺼져 있어 실제 이미지 빌드·Caddy 기동·TLS 발급은 이 환경에서 실행하지 못했다.

## 계약 교차 검토

- 외부 노출은 `frontend`의 `80:80`, `443:443`뿐이다. `backend`는 `expose: 8080`만 사용하므로 Compose 네트워크 안의 `backend:8080`에서만 접근된다.
- Caddy의 `handle /api/*`, `handle /files/*`가 SPA fallback보다 먼저 처리된다. 나머지는 `try_files {path} /index.html`로 React Router의 직접 진입도 유지한다.
- Caddy는 `APP_DOMAIN` 런타임 환경변수로 사이트 주소를 정하고, `caddy_data`·`caddy_config` named volume에 HTTPS 인증서·설정을 보존한다.
- 백엔드만 `env_file: backend/.env`를 받는다. DB·JWT·관광공사·카카오 REST/시크릿은 프런트 빌드·Caddy 환경에 전달되지 않는다. `VITE_KAKAO_JS_KEY`만 공개 브라우저 키로 프런트 빌드 인자에 넣으며, 코드의 실제 환경변수 이름과 일치한다.
- 프런트·백엔드 `.dockerignore`는 로컬 `.env`를 빌드 컨텍스트에서 제외한다. Dockerfile에는 서버 비밀을 `COPY`, `ARG`, `ENV`로 넣는 경로가 없다.
- Compose는 `APP_AUTH_REFRESH_COOKIE_SECURE=true`를 백엔드에 강제해 HTTPS 단일 도메인에서 refresh HttpOnly 쿠키가 Secure로만 발급된다. 기존 `gradlew bootRun`의 로컬 HTTP 기본값은 바뀌지 않는다.
- 업로드는 `itp-uploads:/app/uploads`의 기존 LocalFileStorage 계약을 유지하며, Supabase PostgreSQL은 Compose 외부 DB로 유지된다.

## 배포 전 입력 조건

현재 로컬 `backend/.env`에는 새 `APP_DOMAIN`, `VITE_KAKAO_JS_KEY`가 아직 없을 수 있다. 실제 배포 전 `backend/.env.example`을 기준으로 두 값을 채워야 Compose의 required-variable 검사를 통과한다. `APP_DOMAIN`에는 `https://` 없이 DNS가 서버를 가리키는 실제 도메인을 사용해야 Caddy가 인증서를 발급할 수 있다.

## S3 미구현 제한

S3/Supabase Storage는 아직 구현되지 않았다. `itp-uploads`는 한 Docker 호스트의 로컬 named volume이므로 컨테이너 재생성에는 남지만, 서버·볼륨 손실과 다중 서버 배포에는 사용자 사진을 보장하지 못한다. 현재 배포 구성은 단일 서버 임시 운영에 한정한다.

## 검증

- `APP_DOMAIN`, `VITE_KAKAO_JS_KEY`에 안전한 placeholder를 주입한 `docker compose config -q` 통과
- `npm run build` 통과 (기존 500kB 청크 권고 경고만 출력)
- 이전 항목에서 `./gradlew.bat bootJar` 통과
- `git diff --check` 통과 (기존 CRLF 변환 경고만 출력)
- `docker compose build`·`up`은 Docker Desktop Linux 엔진 미기동으로 미실행 (`//./pipe/dockerDesktopLinuxEngine` 없음)

## 운영 권고

- 서버에서 Docker Desktop/Engine을 실행한 뒤 실제 도메인 DNS 상태로 `docker compose up --build`를 수행하고, `/api/v1` 프록시·SPA 새로고침·로그인 refresh 쿠키의 `Secure` 속성·인증서 자동 발급을 확인한다.
- 객체 스토리지와 백업·복구 정책은 다중 서버 또는 장기 배포 전에 별도 작업으로 전환한다.
