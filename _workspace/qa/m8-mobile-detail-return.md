# M8 수상작 상세 뒤로가기 모바일 QA

## 검토 범위

- 수상작 목록(`/contests`)에서 상세(`/contests/:id`)로 들어간 뒤의 복원 동작
- 모바일 브라우저 뒤로가기·기기 뒤로가기와 상세 화면의 화면 내 뒤로가기 링크
- 홈·혼잡도·마이·지도·직접 URL처럼 목록 이외의 진입 경로

## 코드 기반 확인 (재검토: 2026-08-18)

1. 목록 카드의 `onOpen`은 현재 목록 히스토리 항목에 `contestListRestore`를 기록한다. 값에는 목록 location key, 적용된 `ContestQuery`, 현재 `window.scrollY`가 포함된다.
2. 목록 카드의 Link는 상세 entry에 `state: { contestListEntry: true }`를 전달한다.
3. 상세의 화면 내 뒤로가기 버튼은 위 state가 있을 때 `navigate(-1)`을 실행한다. 따라서 모바일 기기·브라우저 뒤로가기와 화면 내 버튼 모두 같은 목록 history entry에 돌아가며, `ContestListPage`의 복원 로직이 적용된다. viewport 종류를 구분하지 않으므로 모바일과 데스크톱의 규칙은 같다.
4. 홈·혼잡도·마이·지도·직접 URL처럼 state가 없는 진입은 `navigate('/contests')`로 폴백한다. 이 경로는 잘못된 history back으로 외부 화면 또는 빈 history로 나가는 일을 막는다.

## 통합 판정

**통과 (코드 및 빌드 기준).** 모바일 UI의 화면 내 뒤로가기와 기기·브라우저 뒤로가기가 목록 진입일 때 같은 복원 경로를 사용한다. `npm run build`도 통과했다. 실제 360px 브라우저에서의 위치 오차만 수동 확인하면 된다.

## 권고 구현 기준

- 목록에서 온 상세는 동일한 history entry로 되돌아가야 한다. 화면 내 뒤로가기와 기기/브라우저 뒤로가기의 결과를 같게 만든다.
- 목록 이외의 진입은 출발한 화면의 history를 우선 보존한다. 직접 URL 또는 history에 이전 앱 화면이 없는 경우에만 `/contests`로 안전하게 폴백한다.
- 목록 복원은 모바일 360px와 데스크톱 모두 동일하게: 필터·모바일 열 수·이미 로드한 페이지가 유지되고, 카드의 화면상 위치가 기존 위치와 실질적으로 같아야 한다.
- 복원은 한 번만 실행해야 하며, 무한 스크롤의 다음 페이지 로딩이나 이미지 높이 확정 뒤 다시 상단으로 튀면 안 된다.
- 모바일 하단 탭으로 다른 탭을 누르는 것은 명시적 새 탐색이므로 과거 목록 위치를 강제 복원하지 않는다.

## 수동 QA 시나리오

1. 360px에서 수상작 목록을 3페이지 이상 내리고 필터 하나를 적용한 뒤 카드 선택 → 기기 뒤로가기 → 같은 카드 부근, 같은 필터/2열 또는 선택 열 상태인지 확인.
2. 같은 흐름에서 상세 상단 뒤로가기 버튼 선택 → 위와 동일한 위치로 돌아오는지 확인.
3. 홈 대표작, 혼잡도 연관 수상작, 마이 저장 수상작, 지도 핀 각각에서 상세 진입 → 화면 내 뒤로가기와 기기 뒤로가기 모두 원래 진입 흐름을 훼손하지 않는지 확인.
4. `/contests/:id`를 주소로 직접 열고 새로고침 → 화면 내 뒤로가기가 빈 페이지/외부 사이트로 이동하지 않고 `/contests`로 안전하게 처리되는지 확인.
5. 상세에서 로그인 유도·좋아요·지도 조작 후 뒤로가기 → 목록 상태가 덮어써지지 않는지 확인.

## 남은 위험

- 현재 목록 상태에는 로드된 페이지 수 자체를 직렬화하지 않는다. TanStack Query 캐시가 사라진 새로고침/긴 유휴 뒤에는 높은 scrollY를 즉시 복원하면 콘텐츠 높이가 부족할 수 있다. 이번 요구에서는 같은 SPA 세션의 뒤로가기를 보장하고, 영속 복원은 별도 범위로 분리하는 편이 안전하다.
- `contestListEntry`는 상세 entry의 navigation state라서 주소를 복사해 새 탭으로 열면 전달되지 않는다. 이 경우 `/contests` 폴백이 의도된 동작이다.
