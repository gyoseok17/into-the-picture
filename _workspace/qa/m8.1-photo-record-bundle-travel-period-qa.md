# M8.1 사진 묶음 여행 기간(시작일·종료일) 설계·QA 점검

작성일: 2026-08-31
상태: 구현 반영 회귀 체크리스트

## 현재 모델과 영향 범위

- 새 업로드 묶음은 `photo_record_bundle`에 공통 `takenAt` 하나를 저장하고, 하위 `photo_record`도 같은 값으로 저장한다.
- 기존 단일 기록은 `bundle_id = NULL`인 legacy이며 자체 `photo_record.taken_at`만 가진다.
- 스토리는 bundle DTO의 `takenAt`으로 날짜 그룹을 만들고, null이면 `createdAt`으로 fallback한다.
- 지도는 bundle/legacy 하나를 방문 기록으로 다루며, 위치 키와 대표 설정은 사진 record ID를 참조한다. 기간은 위치 그룹·마커 수·대표 FK를 바꾸면 안 된다.

## 권장 데이터·API 계약

### 저장 위치

- 여행 기간은 **bundle에만** 기존 `takenAt`(시작일)과 새 `endedAt`(종료일)으로 둔다. 하위 사진의 EXIF 시각과 지도·대표의 기준은 바꾸지 않는다.
- `endedAt`은 선택값이다. 종료일만 단독 입력은 허용하지 않고, 종료일이 있으면 시작일(`takenAt`)이 반드시 있어야 한다.
- 둘 다 있으면 `takenAt <= endedAt`을 서버에서 검증한다. 같은 날은 당일 여행으로 유효하다.
- 기존 bundle/legacy 행은 migration 뒤 기간 값이 null이며, 과거 촬영일을 임의로 기간으로 backfill하지 않는다. 사용자 기억을 추정해 바꾸는 것은 데이터 왜곡 위험이다.
- legacy 단일 기록은 여행 기간을 지원하지 않는다. 향후 legacy를 묶음으로 이관하는 별도 기능이 없다면 API에서도 `endedAt = null`로 일관되게 반환한다.

### DTO/API

- `PhotoRecordBundleDto`, `PhotoRecordBundleMapPinDto`, 프런트 `PhotoRecordBundle`, `PhotoRecordBundleMapPin`, bundle upload input에 같은 이름·nullability의 `endedAt`을 추가한다.
- multipart 업로드는 기존 `takenAt=YYYY-MM-DD`와 선택 `endedAt=YYYY-MM-DD`을 받는다. 잘못된 형식·종료일 단독·시작일보다 이른 종료일은 400이다.
- 기존 `takenAt`은 묶음 시작일과 기존 정렬 호환용으로 유지한다. 기간을 입력해도 하위 사진의 `takenAt`은 시작일로 저장한다.
- 기간 수정 API가 이번 범위에 없다면 새 업로드에서만 설정 가능하다는 사실을 UI·기록에 명시한다. 편집 UI가 생기면 bundle 소유권 검증과 같은 날짜 검증을 재사용한다.

## 스토리 타임라인 규칙

- 스토리의 일자 노드는 묶음 시작일 `takenAt`을 우선 사용하고, 없으면 `createdAt` fallback을 유지한다.
- 종료일은 카드/폴라로이드 하단에 `8. 29. ~ 8. 31.`처럼 여행 기간 설명으로만 노출할 수 있으며, 시작일과 종료일 사이의 빈 날짜 노드를 만들거나 묶음을 여러 날짜에 복제하지 않는다.
- 기간이 1일이거나 종료일이 없으면 중복 범위 표현을 피하고 시작일(또는 기존 촬영일)만 보인다.
- 기존 legacy와 기간 없는 bundle은 현재 날짜 그룹·정렬 결과가 한 글자도 달라지지 않아야 한다.

## 지도·대표 기록 상호작용

- 지도 마커의 기록 수는 여전히 bundle/legacy 수다. 기간 일수·사진 수가 marker count에 더해지지 않는다.
- 위치 그룹(`CITY`/`PLACE`)과 `photo_map_location_representative.representative_photo_id`는 기간과 무관하다. 기간 변경/입력으로 대표 설정이 사라지거나 다른 위치로 옮겨지면 안 된다.
- 동일 위치에 여러 방문 bundle이 있을 때 대표 fallback의 최신 판단은 기존 `coalesce(takenAt, createdAt)` 규칙을 유지한다. 기간 시작일을 최신 기준으로 바꾸려면 별도 명시 계약·마이그레이션이 필요하다.
- map pin 응답에 기간을 추가해도 지도 카드의 대표 사진·내역 선택·다장 사진 index 동작은 유지한다. 기간 미표시라도 DTO 확장은 소비자 타입과 함께 적용한다.

## 수동 QA 체크리스트

### 데이터·입력

- [ ] 새 묶음: 시작 8/29, 종료 8/31 저장 후 DB와 GET bundle DTO가 정확히 같은 날짜를 반환한다.
- [ ] 새 묶음: 시작=종료 저장 성공.
- [ ] 시작만 저장 성공, 종료만 저장·종료<시작·잘못된 날짜 형식은 400이며 bundle/파일이 생성되지 않는다.
- [ ] 기간 없이 저장한 새 묶음, migration 전 기존 묶음, legacy 단일 기록이 모두 기존대로 조회/삭제/보관된다.
- [ ] 다른 사용자 bundle ID로 기간 수정(해당 API가 생길 경우)은 404/권한 오류이며 존재 여부·기간을 노출하지 않는다.

### 스토리

- [ ] 8/29~8/31 bundle은 8/29 그룹에 카드 하나만 나오며 8/30·8/31 빈 노드는 생기지 않는다.
- [ ] 같은 시작일의 여러 bundle은 한 날짜 그룹에 모두 보이고, 각자 기간 표시는 섞이지 않는다.
- [ ] 기간 없는 bundle/legacy는 takenAt→createdAt fallback 그룹이 이전과 동일하다.
- [ ] 기간 카드의 대형 뷰어, 관리 선택, 보관/복원, 삭제 후 그룹 제거가 기존 카드와 동일하게 동작한다.

### 지도·대표

- [ ] 기간 있는 bundle과 기간 없는 bundle이 같은 시군에 있을 때 마커는 방문 기록 2건이며 사진 수·3일 기간으로 늘어나지 않는다.
- [ ] 과거 기간 bundle을 대표로 지정한 뒤 map 재조회·앱 새로고침에서도 해당 record가 대표이다.
- [ ] 대표 bundle을 삭제하면 preference FK가 null 처리되고 기존 최신 fallback record가 대표가 된다. 기간 정보가 남은 고아 preference가 없어야 한다.
- [ ] 기간이 있는 다장 묶음의 지도 내역 선택 후 사진 이동, 다른 단장 기록 전환에서 photo index 범위 오류가 없다.

## 차단 위험

- 기존 `takenAt` 의미를 시작일로 덮어써 사진 정렬·대표 fallback·legacy 표시를 바꾸는 것.
- 종료일 단독 또는 종료<시작을 서버가 허용하는 것.
- 기간 하루마다 스토리/지도 기록을 복제해 마커 수나 삭제 대상이 달라지는 것.
- migration이 기존 bundle/record의 날짜를 추정·수정하거나 대표 설정 참조를 깨는 것.

위 항목 중 하나라도 발생하면 **차단**이다. 기간 텍스트 포맷, 표시 위치 같은 표현 차이는 사용자 확인 전 권고다.

## 사진별 촬영일과 여행 기간 분리 계약 (2026-09-01)

### 역할 분리

| 데이터 | 단위 | 의미 | 변경 주체 |
| --- | --- | --- |
| `PhotoRecord.takenAt` | 사진 한 장 | 실제 촬영 시점 | EXIF 우선, 사용자 사진별 수정 가능 |
| `PhotoRecord.takenAtSource` *(신규 권장)* | 사진 한 장 | 촬영일 값의 출처 | `EXIF`, `MANUAL`, `BUNDLE_START_FALLBACK`, `UNKNOWN` |
| `PhotoRecordBundle.startedOn/endedOn` | 사진 묶음 | 사용자가 기록한 여행 기간 | 묶음 업로드/기간 편집 |

- EXIF에서 얻은 촬영일은 파일마다 보존한다. 묶음 기간 시작일을 입력해도 EXIF가 있는 사진의 `takenAt`을 덮어쓰지 않는다.
- 사용자는 파일별 촬영일을 직접 수정할 수 있고, 수동 입력은 EXIF보다 우선한다. 이후 여행 기간을 바꿔도 수동 입력값을 덮어쓰지 않는다.
- EXIF도 수동값도 없는 사진만 묶음 시작일을 `takenAt`의 fallback으로 사용한다. 시작일도 없으면 `takenAt=null`로 둔다.
- fallback으로 채운 값은 실제 촬영일로 오인되지 않게 출처를 함께 저장·응답한다. 이는 이후 공모전 사진 비교에서 날짜 확정 여부를 물을 수 있는 근거다.
- 하위 사진의 실제 촬영일이 서로 달라도 묶음·여행 기간·장소·지도 위치는 하나의 방문 기록으로 유지한다.

### API/저장 계약

- bundle multipart 업로드는 파일마다 확정된 `takenAt`과 출처를 전달/보존할 수 있어야 한다. 단일 공통 `takenAt`만 받아 모든 사진에 복사하는 기존 계약은 이 요구를 충족하지 못한다.
- 사용자 수동 보정은 사진 record ID 단위 update API로 명시한다. bundle 기간 API와 분리해 잘못된 일괄 변경을 막는다.
- GET bundle/map DTO의 `photos[]`에는 각 사진의 `takenAt`과 `takenAtSource`가 있고, bundle DTO에는 별도 `startedOn/endedOn`만 있다. 두 의미를 같은 필드명으로 재사용하지 않는다.
- 기존 DB의 `PhotoRecord.takenAt` 값은 그대로 `MANUAL` 또는 migration-safe한 `UNKNOWN`으로 보존한다. 과거 값의 진짜 출처를 추정해 `EXIF`로 표기하지 않는다.
- 기존 bundle/legacy에 출처 값이 없으면 null/`UNKNOWN`을 지원하고, 기간 추가 migration은 기존 사진 촬영일을 변경하지 않는다.

### 스토리·지도 사용 규칙

- 스토리 날짜 그룹과 여행 카드 순서는 bundle `startedOn` 우선, 없으면 기존 bundle 정렬 기준(`takenAt`, `createdAt`)을 사용한다. 사진별 `takenAt`이 기간과 다르다고 bundle을 다른 날짜 그룹으로 쪼개지 않는다.
- 폴라로이드/대형 묶음 뷰어에서 사진별 촬영일을 노출할 경우 출처에 따라 `EXIF 촬영일`, `직접 기록한 날짜`, `여행 시작일 기준`처럼 구분 가능해야 한다. 사용자에게 필요 없으면 숨기되 비교 확인 흐름이 읽을 수 있는 데이터는 유지한다.
- 지도 marker·대표 설정·위치 키는 bundle 장소/지도 위치와 record ID 기준을 그대로 쓴다. 사진별 촬영일과 기간이 marker 수·대표 후보·위치를 바꾸면 안 된다.
- 대표 fallback의 최신 판단은 명시적으로 bundle `startedOn` 우선인지 기존 record `takenAt` 우선인지 한 가지로 고정해야 한다. 기간 도입만으로 암묵적으로 바꾸지 않는다.

### 수동 QA 체크리스트

- [ ] 3장 업로드: A=EXIF 8/29, B=EXIF 8/30, C=없음 + 여행 8/29~8/31. A/B 날짜 보존, C만 8/29 fallback·출처 표시.
- [ ] A의 날짜를 8/28로 직접 수정한 뒤 기간을 8/30~9/1로 변경. A는 8/28 `MANUAL`, B는 EXIF 그대로, C만 새 시작일 8/30 fallback.
- [ ] 기간 없이 EXIF 없는 사진 업로드: `takenAt=null`, `UNKNOWN`; 날짜 미상 표시와 기존 story fallback이 안전하다.
- [ ] 같은 묶음의 서로 다른 촬영일이 스토리에서 카드 3개/날짜 노드 3개로 분리되지 않고 시작일 그룹의 방문 카드 1개로 유지된다.
- [ ] 대형 뷰어에서 A→B→C 전환 시 각 날짜/출처가 사진에 맞고, 다장→단장 전환의 index 범위 오류가 없다.
- [ ] legacy 단일 사진, 기존 묶음, 새 기간 묶음이 함께 있을 때 조회·보관·삭제·관리 선택과 API 타입 역호환이 유지된다.
- [ ] 지도에서 이 묶음은 기간 3일·사진 3장이어도 방문 기록 1건이며, 대표 지정/삭제 fallback 뒤 출처 데이터가 손실되지 않는다.

### 차단 위험 추가

- EXIF 또는 수동 사진별 날짜를 bundle 시작일로 무조건 덮어쓰는 것.
- fallback 날짜를 EXIF/직접 입력처럼 표시하거나 출처를 응답에서 잃는 것.
- 사진별 촬영일 차이로 하나의 방문 묶음을 스토리/지도에서 여러 방문으로 복제하는 것.
- 기간 편집이 사진 record의 수동·EXIF 날짜를 일괄 변경하는 것.
