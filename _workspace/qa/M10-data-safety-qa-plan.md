# M10 데이터 안전성·조회 성능 QA 계획

- 작성일: 2026-09-20
- 역할: QA·보안 검토
- 범위: 앨범 묶음 삭제의 DB·파일 저장소 일관성, 소유권·API 호환성, 앨범·즐겨찾기 목록의 반복 조회 제거

## 사전 점검 결과

### 1. 묶음 삭제의 현재 위험

- `PhotoRecordBundleService.delete`는 자식 기록을 순서대로 `UserPhotoService.deleteIncludingComparison`으로 삭제한 뒤 묶음을 삭제한다.
- 각 자식 삭제는 DB 행을 삭제한 직후 파일 저장소(`FileStorage.delete`)를 삭제한다. S3와 로컬 파일 시스템은 Spring DB 트랜잭션에 참여하지 않는다.
- 따라서 앞선 파일 삭제는 성공하고 뒤의 파일 삭제 또는 DB 작업이 실패하면 DB 트랜잭션은 되돌아가지만 앞서 삭제한 실제 파일은 되돌릴 수 없다. 현재의 “부분 삭제가 커밋되지 않는다” 주석은 파일 저장소까지 포함하면 사실이 아니다.

### 2. 현재 권한·계약 보호

- 묶음 삭제는 `findByIdAndUserId(bundleId, userId)`로 소유자만 조회한다.
- 자식 중 수상작 비교 연결이 하나라도 있으면 파일 삭제 전에 `CONFLICT`로 중단한다.
- 개별 파일 읽기는 `findOwnedRecord` 뒤에 저장소를 읽으므로 소유권 검사 후 접근한다.
- API 응답 형식과 삭제 성공 상태(`204`)는 변경하지 않아야 한다.

### 3. N+1 확인 대상

- 앨범 목록: 묶음 1회 조회 뒤 `dto(bundle)`가 묶음마다 `findAllByBundleId...`를 호출한다. 목표는 묶음 수와 관계없이 자식 기록 조회를 한 번으로 제한하는 것이다. 레거시 단일 기록 조회는 별도 1회가 허용된다.
- 즐겨찾기 목록: 즐겨찾기 1회 조회 뒤 각 즐겨찾기의 `contestRepository.findById`가 반복된다. 목표는 대상 수와 관계없이 수상작 조회를 한 번으로 제한하고, 존재하지 않는 수상작 연결은 기존처럼 목록에서 제외하는 것이다.

## QA 차단 기준

1. 파일 삭제 실패 시 DB가 되돌아가더라도 이미 삭제된 파일이 복구 불가능하게 남는 설계면 차단한다.
2. 삭제 대상·자식 기록·파일이 다른 사용자 소유일 가능성을 열거나, 비교 연결된 사진 삭제 방어가 약해지면 차단한다.
3. 기존 `DELETE /me/photo-bundles/{bundleId}`의 `204`, `404`, `409` 의미가 달라지면 차단한다.
4. 앨범 목록이 묶음 수만큼 자식 조회하거나, 즐겨찾기가 대상 수만큼 수상작 조회하면 차단한다.
5. 삭제 실패·빈 목록·삭제된 수상작 참조에서 예외가 사용자 API까지 누출되면 차단한다.

## 구현 도착 후 교차 검증 계획

- 삭제 작업을 DB 커밋 이후 비동기 파일 삭제로 미루는 경우: 실패 재시도/고아 파일 허용 범위와 사용자 응답을 확인한다.
- 삭제 작업을 파일 백업·복구 방식으로 바꾸는 경우: 원본 키 복구 가능성, S3·로컬 어댑터 동등성, 실패 순서를 검증한다.
- 앨범: 2개 이상 묶음과 레거시 기록을 섞어 DTO 사진 순서·정렬·필드가 이전과 같은지 검증하고 repository 호출 횟수를 테스트한다.
- 즐겨찾기: 여러 즐겨찾기와 존재하지 않는 외부 ID를 섞어 정렬·누락 규칙과 수상작 일괄 조회 횟수를 테스트한다.
- 관련 백엔드 테스트와 전체 `gradlew.bat test`, 프런트 API 타입/빌드, `git diff --check`를 교차 확인한다.

## 남은 위험

- DB와 객체 저장소 간 분산 트랜잭션은 제공되지 않는다. 구현은 복구 불가능한 사용자 파일 손실을 막는 쪽을 우선하고, 일시적 고아 파일은 재시도 또는 운영 정리 대상으로 명시해야 한다.

## 최종 교차 검증 (2026-09-20)

### 검증한 변경

- `AfterCommitFileDeletion`은 Spring 트랜잭션 동기화가 있을 때만 `afterCommit` 콜백에 파일 삭제를 등록한다. 롤백이면 콜백이 실행되지 않아 DB에 복원된 사진이 이미 지워진 파일을 가리키지 않는다.
- 파일 저장소 삭제 실패는 커밋 뒤에 로그로 남기고 API 실패로 되돌리지 않는다. 따라서 성공 응답 뒤 고아 파일이 남을 수는 있지만, 사용자 기록·파일의 복구 불가능한 불일치보다 안전하다.
- 묶음 삭제의 소유권 조회(`findByIdAndUserId`)와 수상작 비교 연결 사전 `409 CONFLICT` 방어는 유지됐다. 삭제 API의 경로·응답 DTO·`204`/`404`/`409` 의미도 바뀌지 않았다.
- 앨범 목록은 묶음 1회, 해당 묶음 자식 기록 일괄 1회, 레거시 단일 기록 1회로 바뀌었고, 목록 조립 중 묶음별 조회가 발생하지 않는다.
- 즐겨찾기 목록은 유효한 수상작 ID를 한 번에 조회하고 원래 favorite 정렬을 보존한다. 존재하지 않거나 숫자가 아닌 `externalId`는 기존과 동일하게 결과에서 제외한다.
