# M8.1 사진 묶음 통합 QA·보안 체크리스트

작성일: 2026-08-28
기준 계약: `_workspace/contracts/M8.1-photo-record-bundles.md`
상태: 구현 도착 전 정적 계약 검토 완료, 실행 검증 대기

## 현재 정적 판정

- 현재 프런트는 `POST /me/photos`를 파일별로 최대 3개 동시 요청하는 기존 `BatchPhotoUploadPanel` 구조다. 계약의 `POST /me/photos/bundles` 단일 multipart 요청·묶음 응답을 아직 소비하지 않는다.
- 현재 백엔드 검색 결과에는 `photo_record_bundle` 엔티티·마이그레이션·`/me/photos/bundles` 컨트롤러가 아직 확인되지 않는다. 아래 항목은 구현 도착 뒤 차단 검증 대상이다.
- 기존 개별 사진·비교 API가 이미 `PhotoRecord`를 공용 기반으로 사용하므로, 묶음 삭제의 비교 참조 409은 특히 `bundle` 전체와 각 하위 record를 함께 검사해야 한다.

## DB 호환·마이그레이션

- [ ] `photo_record_bundle` 생성은 기존 `photo_record`/`user_photo`/비교 레코드를 수정·삭제하지 않는다.
- [ ] `photo_record.bundle_id`는 nullable FK이며 기존 직접 업로드·비교 사진은 `NULL`로 유지된다.
- [ ] 묶음 FK 삭제 정책이 명시돼 있다. 묶음을 삭제할 때만 하위 `photo_record`를 함께 삭제하고, 사용자·다른 묶음·공모전 레코드에는 cascade가 닿지 않는다.
- [ ] 사용자 소유자 FK와 `user_id + bundle_id` 조회 인덱스, 활성/보관 목록에 필요한 정렬 인덱스가 있다.
- [ ] 기존 V5/V6/V9 마이그레이션 적용 DB에서 새 migration을 반복 실행해도 실패·데이터 소실이 없다.
- [ ] 롤백은 새 bundle 테이블/nullable 컬럼만 되돌릴 수 있고 기존 사진 파일·비교 참조를 삭제하지 않는다.

## API 계약·입력 검증

- [ ] `POST /me/photos/bundles`는 인증된 사용자만 접근하고 `files` 1~20개를 검증한다. 빈 배열, 21개, null file, 허용하지 않은 MIME/확장자는 400이다.
- [ ] 공통 `takenAt`, `placeName`, `mapRegionCode`, `mapCityCode`, `memo`가 반환된 bundle과 모든 하위 사진에 같은 의미로 나타난다.
- [ ] 지도 코드/도시 코드는 서버 카탈로그가 검증한다. 다른 권역의 도시 조합은 400이며 클라이언트 값만 신뢰하지 않는다.
- [ ] 응답 DTO가 `bundleId`, 공통 메타데이터, 하위 사진 id/url/originalFilename/createdAt를 명확히 구분하며, 프런트 타입과 정확히 일치한다.
- [ ] `GET /me/photos/bundles?archived=false`는 묶음과 legacy 개별 사진을 구별 가능한 동일 목록 계약으로 반환한다. `archived=true`와 빈 목록도 확인한다.
- [ ] `DELETE /me/photos/bundles/{id}`의 204/404/403/409 오류 형태가 프로젝트 표준 오류 DTO와 일치한다.

## 소유권·파일 보안

- [ ] 조회·업로드·삭제 모두 path의 bundle id만으로 접근하지 않고 서버에서 `user_id`를 대조한다.
- [ ] 다른 사용자의 bundle id 조회/삭제는 존재 여부를 노출하지 않는 404 또는 프로젝트 표준 권한 오류로 처리한다.
- [ ] 묶음 안의 모든 하위 record/file이 같은 사용자 소유인지 서버에서 보장한다. 요청 body의 user id나 file URL은 신뢰하지 않는다.
- [ ] 파일 저장 중 실패한 파일은 외부 접근 가능한 orphan 파일로 남지 않는다. 저장 키는 사용자 경계를 벗어나지 않는다.

## 원자성·부분 실패

- [ ] 20개 중 1개 파일 저장/DB 기록/이미지 검증이 실패하면 성공한 파일·bundle row·파일 저장소를 모두 보상 삭제하고 요청 전체 실패로 끝난다.
- [ ] DB 트랜잭션 롤백 뒤에도 저장소 파일이 남지 않으며, 저장소 삭제 실패는 재시도/운영 로그 대상이다. 사용자에게 성공으로 보이지 않는다.
- [ ] 네트워크 중단/동일 요청 재시도에서 중복 bundle이 생기지 않도록 요청 상태 또는 멱등성 전략을 확인한다.
- [ ] 프런트는 단일 요청 실패 시 부분 성공 수를 표시하지 않고, 재시도 가능한 실패 안내를 제공한다. 기존 개별 업로드의 파일별 재시도 UX를 그대로 혼용하지 않는다.

## 비교 참조 삭제 409

- [ ] 묶음 하위 record 중 하나라도 `contest` 비교 참조가 있으면 `DELETE bundle`은 409이고, bundle·하위 photo record·원본 파일은 하나도 삭제되지 않는다.
- [ ] 409 응답에는 "비교에 사용 중인 사진"이라는 사용 가능한 안내와 충돌 사진/비교 수(가능하면)가 들어간다. 단 내부 타 사용자 정보는 노출하지 않는다.
- [ ] 비교를 먼저 삭제하거나 비교 사진 교체 뒤에는 동일 bundle 삭제가 성공한다.
- [ ] legacy 개별 사진 삭제의 기존 409 및 `deleteIncludingComparison` 동작이 묶음 도입 뒤에도 달라지지 않는다.

## 스토리·맵·일괄 삭제 UI

- [ ] 스토리는 bundle을 한 카드로 표시하고 사진 수·공통 날짜·장소·대표 이미지를 보여 준다. legacy 사진은 기존 개별 카드로 보인다.
- [ ] 카드 클릭은 해당 bundle의 모든 사진을 열고, 숨김/보관 상태는 active/archive 모두 일관되게 반영한다.
- [ ] 맵은 bundle을 핀 하나로 표시하고, 장소 좌표 우선·도시 대표 좌표 보조 규칙을 유지한다. 하위 사진을 클릭하면 모두 확인 가능하다.
- [ ] 관리 모드에서 bundle과 legacy 사진을 동시에 다중 선택할 수 있으나, 삭제 확인에는 각각의 수와 영향(묶음 전체 사진 수)을 명확히 표시한다.
- [ ] 삭제 중 중복 클릭·다중 요청은 막고, 성공 시 story/map/archive/user-photo/comparison 캐시를 필요한 범위만 갱신한다.
- [ ] 409은 선택 상태를 유지하고 해당 묶음을 식별해 안내한다. 401/403/500/네트워크 실패도 선택을 잃지 않고 재시도 수단을 제공한다.

## 실행 검증 순서

1. 깨끗한 사용자 A로 1장·3장·20장 묶음을 각각 업로드하고 GET/스토리/맵/보관함을 대조한다.
2. 사용자 B로 A의 bundle id를 GET/DELETE해 권한 경계를 확인한다.
3. 파일 1개를 의도적으로 실패시키고 DB row·저장 파일·GET 결과가 모두 0인지 확인한다.
4. 묶음 사진 하나로 비교를 만든 뒤 bundle DELETE 409, 비교 삭제 후 DELETE 204, 파일 URL 404 순서를 확인한다.
5. legacy 단일 사진과 비교 사진을 섞어 story/map/다중 선택 삭제를 회귀 테스트한다.

## 통합 판정 기준

DB 보존, 서버 소유권, 부분 실패 원자성, 비교 참조 409 중 하나라도 미충족이면 **차단**이다. 화면 표현/문구만의 차이는 권고로 기록하되, 실제 삭제 대상이나 사진 수를 오해하게 하면 차단으로 올린다.

### 계약/API 대조: 통과

- `V10__add_photo_record_bundles.sql`은 새 `photo_record_bundle`과 nullable `photo_record.bundle_id`만 추가한다. 기존 `photo_record` 데이터 수정·삭제는 없다. bundle/user 및 record/bundle 조회 인덱스도 있다.
- `PhotoRecordBundleController`는 계약의 POST/GET/DELETE와 map GET을 모두 `/me/photos/bundles` 아래에 제공한다. POST는 `files` 반복 multipart 필드, 1~20 검증, 201 DTO 반환을 사용한다.
- `PhotoRecordBundleDto`와 프런트 `PhotoRecordBundle`, map DTO와 `PhotoRecordBundleMapPin`의 필드 구조는 대조 결과 일치한다. 지도 위치 카탈로그 DTO도 `code/label/latitude/longitude`로 일치한다.
- 프런트는 묶음 업로드에 단일 `POST /me/photos/bundles`를 사용하며, 기존 파일별 동시 업로드 경로는 batch panel에서 제거됐다. 결과 캐시는 bundles, bundle-map, legacy records, user photos, comparisons까지 무효화한다.

### 소유권·삭제 409: 통과

- bundle 삭제는 `findByIdAndUserId(bundleId, userId)`로 먼저 소유권을 확인한다. 타 사용자/없는 bundle은 표준 NOT_FOUND 경로이며 하위 record를 직접 path로 조회해 삭제하지 않는다.
- 모든 하위 record의 `contest != null`을 삭제 전에 검사한다. 하나라도 비교 참조면 409을 던지고, record/file/bundle 삭제 호출 전 종료한다. 단위 테스트가 이 순서를 검증한다.
- 비교 참조가 없을 때는 record/file을 먼저 지우고 bundle을 마지막에 삭제한다. FK cascade에 의존하지 않아 기존 개별 사진·비교 API의 동작을 바꾸지 않는다.

### DB/부분 실패 검토: 조건부 통과

- 서비스와 개별 업로드가 같은 Spring transaction에서 동작하고, bundle 업로드 중 `RuntimeException`이면 DB transaction은 롤백된다. 이미 생성된 하위 record의 실제 파일은 보상 삭제를 시도한다.
- 다만 `LocalFileStorage.store()`가 파일 복사 중 `IOException`을 내기 전에 대상 파일을 부분 생성하는 경우, `StoredFile`을 반환하지 못해 보상 삭제 대상에 포함되지 않을 수 있다. 또한 파일 삭제 `IOException`은 현재 무시한다. 일반 성공/검증 실패 경로는 안전하지만, 저장소 I/O 장애까지 포함한 무고아 파일 보장은 아직 검증되지 않았다.
- 현재 테스트는 21개 거부와 409만 다룬다. 1/20개 성공, 중간 파일 실패의 DB+실파일 보상, 타 사용자 bundle 404, migration 적용 DB 회귀를 실행하는 통합 테스트가 추가되어야 한다.

### 프런트 일괄 삭제 검토: 권고(데이터 표현 주의)

- 관리 모드의 `Promise.all` 삭제에서 선택 항목 하나가 409이어도 동시에 시작된 다른 항목은 성공할 수 있다. 화면은 catch 후 선택을 유지하지만, 어떤 항목이 삭제됐고 어떤 항목이 409인지 개별 결과를 표시하지 않는다.
- 서버 단일 bundle 삭제의 원자성은 통과한다. 다만 여러 bundle을 한 번에 지우는 UI는 성공/충돌 결과를 분리해 알리거나, 비교 참조 여부를 먼저 확인한 뒤 순차 삭제해야 사용자가 실제 삭제 결과를 오해하지 않는다.

**조건부 통과(커밋 전 권고 해소 또는 잔여 위험 기록 필요).** 계약·DTO·소유권·개별 bundle 409·빌드는 통과했다. 저장소 I/O 보상과 다중 선택 삭제 결과 표시는 아직 실행 검증되지 않았으며, 파일 잔존 위험과 부분 성공 안내는 배포 전 보완 권고다.

### 보완 재검증 — 2026-08-28

- `LocalFileStorage.store()`는 최종 경로가 아닌 사용자 디렉터리의 임시 파일에 먼저 복사한 뒤 원자 이동을 시도한다. 복사·이동 실패 시 임시 파일을 삭제하고, 정리 실패는 원래 예외의 suppressed exception으로 보존한다. 따라서 업로드 스트림 실패가 최종 파일 또는 임시 파일 고아로 남는 이전 차단 우려는 해소됐다.
- `LocalFileStorageTest.removesTheTemporaryFileWhenCopyingTheUploadFails`가 스트림 `IOException` 뒤 사용자 저장소 디렉터리가 비어 있는지 검증한다. 경로 이탈 삭제 거부 테스트도 유지된다.
- 앨범 다중 삭제는 `Promise.all` 동시 요청 대신 선택 항목을 순차 처리한다. 성공한 항목만 선택 상태에서 제거하고, 완료·비교 사진 충돌(409)·실패 건수를 사용자에게 함께 표시한다. 따라서 일부 성공이 발생해도 결과가 숨겨지지 않는다.
- 재실행 결과: `backend\\gradlew.bat test` 통과, `frontend\\npm run build` 통과, `git diff --check` 오류 없음. 프런트 빌드에는 기존 Vite 500 kB 청크 경고만 남는다.
