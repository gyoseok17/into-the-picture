# M8.1 앨범 개별 사진 → 사진 놓기 계약 검토

## 결론

현재 API만으로 구현할 수 있으므로 서버 API·DTO 변경은 필요 없다. 앨범의 묶음은 화면 표현 단위일 뿐, 각 `photos[]` 항목이 실제 비교 원본인 `PhotoRecord` 식별자를 이미 제공한다.

## 현재 응답과 화면 사용처

| 화면 필요 | 현재 계약 | 판정 |
| --- | --- | --- |
| 앨범에서 개별 사진 선택 | `GET /me/photos/bundles` → `photos[].id` | 충족. `id`는 `PhotoRecord` ID다. |
| 선택 사진이 이미 비교에 연결됨 표시 | `photos[].contestId`, `photos[].displayMode` | 충족. `contestId != null`이면 해당 사진은 비교 기록에 연결돼 있다. |
| 새 비교 대상 수상작 선택 | `GET /me/favorites/contests` | 충족. 서버도 즐겨찾기를 다시 검증한다. |
| 특정 수상작의 기존 결과 확인 | `GET /me/comparisons` → `contest.id`, `id` | 충족. 앨범의 선택 사진과 별개로 이미 그 수상작의 결과가 있는지 확인할 수 있다. |
| 새 비교 생성 | `POST /me/comparisons` with `{ userPhotoId: photos[].id, contestId }` | 충족. 이름은 과거 호환성 때문에 `userPhotoId`지만 값은 실제 `PhotoRecord` ID다. |
| 기존 결과의 사진 교체 | `PATCH /me/comparisons/{comparisonId}` with `userPhotoId` | 충족. |

## 서버 안전 경계

- 생성 시 `findOwnedRecord`로 사진 소유권을 서버에서 확인한다.
- 수상작은 현재 사용자의 `CONTEST` 즐겨찾기가 아니면 `403 FORBIDDEN`이다.
- 사용자·수상작 기준 기존 비교가 있으면 `409 CONFLICT`이며 기존 연결을 덮어쓰지 않는다.
- 선택 사진이 이미 다른 수상작에 연결돼도 `409 CONFLICT`다.
- 묶음 삭제는 연결된 하위 사진이 있으면 `409`로 차단한다. 개별 사진 삭제도 비교 연결 상태를 확인한다.

## 프런트 구현 유의점

- `photos[0]`만 사용하지 말고, 묶음 lightbox/그리드에서 사용자가 누른 개별 `photos[index].id`를 POST에 보낸다.
- `contestId`는 **선택 사진의 연결 상태**, 비교 목록의 `contest.id`는 **수상작 결과 존재 상태**이므로 둘을 함께 사용해야 한다. 다른 사진으로 이미 같은 수상작을 비교한 경우에는 후자를 기준으로 기존 결과로 이동/수정 안내한다.
- 403/409은 사전 조회만으로 생략하지 않는다. 즐겨찾기 해제, 다른 탭의 생성, 직접 요청 상황에서도 서버 응답을 사용자 안내로 변환한다.

## 남은 위험 및 비범위

- 현재 중복 방지는 repository 조회+서비스 검증이다. 동시에 동일 요청이 들어오는 데이터베이스 경쟁 상황까지 강제하는 unique 제약은 이번 UI 변경 범위에 포함하지 않는다.
- `findOwnedRecord`는 보관함(`archivedAt != null`) 사진도 소유 사진으로 인정한다. 앨범 UI가 활성 사진만 선택 대상으로 제한하면 정상이나, 보관함 사진도 비교 금지라는 제품 규칙이 필요하면 별도 서버 변경으로 명시해야 한다.
- 별도 계약 불일치: 프런트 `PhotoTakenAtSource`의 `BUNDLE_FALLBACK`은 서버 enum `BUNDLE_START_FALLBACK`과 다르다. 이번 비교 진입에는 영향 없지만 기간/출처 표시 작업에서 수정이 필요하다.
