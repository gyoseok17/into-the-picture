# M8.1 경상·전라 지도 권역 통합 호환성/QA

작성일: 2026-08-27
범위: 지도 권역을 `GYEONGSANG`, `JEOLLA`로 통합할 때 기존 `GYEONGBUK`·`GYEONGNAM`·`JEONBUK`·`JEONNAM` 사진 기록을 보존하는 방법. 프로덕션 코드 수정 없음.

## 현재 데이터와 목표 코드

현재 저장 가능한 지도 권역 코드는 `GYEONGBUK`, `GYEONGNAM`, `JEONBUK`, `JEONNAM`으로 북/남을 나눠 둔 상태다. 새 지도에서는 아래처럼 canonical 코드 하나로 합긴다.

| 기존 `map_region_code` | 새 canonical `map_region_code` | `map_city_code` |
| --- | --- | --- |
| `GYEONGBUK` | `GYEONGSANG` | 그대로 보존 |
| `GYEONGNAM` | `GYEONGSANG` | 그대로 보존 |
| `JEONBUK` | `JEOLLA` | 그대로 보존 |
| `JEONNAM` | `JEOLLA` | 그대로 보존 |
| 나머지 4개 권역·`NULL` | 변경 없음 | 그대로 보존 |

도시 코드는 이미 고유 코드이고, 대표 좌표도 도시 기준이므로 바꾸지 않는다. 지도에서 대구·포항·부산·울산은 모두 `GYEONGSANG`의 도시 목록으로, 전주·군산·광주·여수 등은 모두 `JEOLLA`의 도시 목록으로 옮긴다.

## 데이터 보존 권장안

1. 새 Flyway 순번(현재 V8가 실행된 환경을 고려하면 V9)을 추가한다. 이미 적용될 수 있는 V8을 수정하지 않는다.
2. V9에서 네 기존 코드만 위 표대로 `UPDATE photo_record SET map_region_code = ...` 한다. `map_city_code`, `latitude`, `longitude`, `geocode_checked_at`, 장소명, 촬영일, 보관/비교 상태는 갱신하지 않는다.
3. 서버 카탈로그의 canonical 목록은 새 두 코드만 내보내고, 각 도시의 소속도 새 권역으로 바꾼다. `GET /me/photos/map/locations`은 새 6개 권역만 반환한다.
4. 배포 직후에도 열린 이전 브라우저 탭·저장되지 않은 draft가 있을 수 있으므로, 서버 입력 검증은 한 릴리스 동안 기존 네 코드를 **입력 별칭(alias)** 으로 받아 새 canonical 코드로 정규화한다. 응답과 새 저장값은 항상 `GYEONGSANG`/`JEOLLA`만 사용한다.
5. 별칭 제거 시점은 이전 프런트가 더 이상 서비스되지 않고, DB에서 legacy 코드 수가 0임을 확인한 다음 별도 마일스톤에 기록한다. 웹 서비스라 해도 장시간 열린 탭을 고려해 즉시 제거하지 않는다.

이 방식은 기존 사진을 삭제·재지오코딩·재업로드하지 않고, 지도 필터 및 도시 앵커를 새 권역 체계로만 바꾼다.

## API/화면 호환 조건

- 일반 사진 DTO와 map DTO는 migration 후 새 `mapRegionCode`를 반환한다. 프런트는 도시 코드만 보고 이전 북/남 권역을 추론하면 안 된다.
- `PATCH`에서 장소명·메모만 바꾸는 기존 사진은 지역값을 건드리지 않는다. 지역을 함께 보낼 때는 legacy 별칭도 새 코드로 정규화한다.
- `POST`의 새 프런트는 `GYEONGSANG`·`JEOLLA`만 보낸다. 캐시된 구 프런트의 legacy 업로드는 임시 별칭으로 성공하되, 응답값은 새 코드라 재조회 시 UI가 새 권역을 표시해야 한다.
- 지도 이미지도 북/남 경계가 여전히 흰 선으로 남아 있으면, 하나의 권역 안에 클릭 불가 선이 남아 사용자에게 모순으로 보인다. 이미지와 SVG 모두에서 내부 북/남 구분은 제거하고, 통합 권역은 하나의 선택 결과를 내는 복수 path 또는 단일 union path로 처리한다.

## QA 체크리스트

### 마이그레이션·DB

- [ ] 마이그레이션 전 legacy 4개 코드별 사진 수를 기록하고, 마이그레이션 후 `GYEONGSANG` 수 = 기존 경북+경남, `JEOLLA` 수 = 기존 전북+전남인지 확인한다.
- [ ] `map_city_code`와 좌표·장소명·촬영일·보관 여부·수상작 연결·원본 파일 참조가 전후 동일한지 표본과 SQL count로 확인한다.
- [ ] `NULL` 지역/도시와 다른 권역은 갱신되지 않는다.
- [ ] Flyway를 새 DB와 V8 적용 DB 양쪽에서 실행해 순번/재실행 오류가 없는지 확인한다.

### 계약·지도

- [ ] 도시 목록 API에 6개 큰 권역만 나오며, 경북/경남 도시가 모두 경상에, 전북/전남 도시가 모두 전라에 정확히 포함된다.
- [ ] 기존 각 4개 권역 사진을 지도·목록·필터에서 열어 새 통합 권역으로 표시되는지 확인한다.
- [ ] 장소 정확 좌표(`PLACE`) 사진은 기존 핀 위치를 유지하고, 도시 앵커(`CITY`) 사진도 같은 도시 위치를 유지한다.
- [ ] legacy 코드로 POST/PATCH한 요청은 정규화되어 성공하고 응답은 canonical 코드다. 잘못된 도시-권역 조합은 여전히 400이다.

### UI·경계·반응형

- [ ] 경상/전라 내부의 기존 북·남 구분선은 클릭 경계가 아니다. 그 선 양쪽을 눌러도 같은 권역 선택으로 이어진다.
- [ ] 경상·전라 각각의 바깥 흰 경계는 기존 QA 기준대로 완전 비클릭이고, 인접 권역으로 넘지 않는다.
- [ ] PC와 320/375/430px 모바일에서 두 통합 영역의 양쪽 끝, 기존 북/남 접점, 도시 목록 전환을 탭/키보드로 확인한다.
- [ ] 선택 후 업로드 → 새로고침 → 지도 재진입에서 통합 권역 강조와 해당 도시 핀이 유지된다.

## 롤백 경계

V9의 데이터 update는 되돌릴 수 있는 명시적 역매핑이 없다. 통합 이후에는 원래 북/남 구분을 사용자 데이터로 복원할 근거가 사라지므로, 배포 전 백업·count 검증이 필요하다. 롤백이 필요하면 단순히 코드/UI만 되돌리지 말고, 별도 보정 migration과 배포 직전 집계 백업을 사용한다.
