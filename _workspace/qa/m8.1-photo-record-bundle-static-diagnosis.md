# M8.1 사진 묶음: 스토리 개별 표시 정적 진단

작성일: 2026-08-28
범위: 코드 수정 없이 다중 업로드 저장·조회 경로와 실행 중 서버 상태를 대조했다.

## 결론

현재 스토리에서 각각 보이는 것은 카드 UI가 묶음을 풀어서 표시한 문제가 아니다. 실행 중 서버가 `GET /api/v1/me/photos/bundles`에서 현재 사진들을 모두 `id: null`, `legacy: true`로 반환하고 있다. 즉 해당 사진들의 `photo_record.bundle_id`가 `NULL`이며, 기존 개별 사진으로 저장된 데이터다.

로그 근거:

- `2026-08-28 23:19:56` 및 `23:20:01`의 `PhotoRecordBundleController#list` 응답이 `PhotoRecordBundleDto[id=null, legacy=true, ...]`로 기록됐다.
- 같은 시점의 `/bundles/map` 응답도 `id=null, legacy=true`다.
- 실행 서버는 Supabase PostgreSQL이고 Flyway 스키마 버전은 `10`이다. 따라서 V10 미적용 또는 예전 서버 실행이 원인은 아니다.

## 코드 경로 대조

- 새 다중 UI `BatchPhotoUploadPanel`은 파일들을 하나의 `FormData` `files` 필드로 모아 `POST /me/photos/bundles`를 호출한다.
- `PhotoRecordBundleService.upload`은 bundle을 먼저 저장하고 각 파일을 `uploadToBundle`으로 저장한다. `uploadToBundle`은 방금 저장된 `PhotoRecord`에 `attachBundle(bundle)`을 호출한다.
- 목록 조회는 실제 bundle 목록과 `bundle IS NULL`인 legacy 목록만 합친다. `PhotoRecordBundleCard`도 bundle 한 개를 카드 한 개로 렌더한다.

따라서 새 endpoint로 저장된 기록의 GET 응답이 `id != null`, `legacy=false`, `photos.length > 1`이면 스토리도 카드 한 장으로 표시되는 구조다.

## 가장 가능성 높은 원인

1. 확인한 사진들은 묶음 기능 반영 전, 또는 기존 단일 업로드 경로(`POST /me/photos`)로 만들어졌다. 기존 데이터를 자동으로 임의 묶음으로 이관하지 않도록 설계되어 있어 정상적으로 legacy 개별 카드로 남는다.
2. 실제 재현 업로드가 새 `POST /me/photos/bundles`가 아니라 단일 endpoint로 나갔는지는 현재 boot 로그에 새 POST 기록이 없어 추가 확인이 필요하다. 브라우저 Network에서 저장 버튼 클릭 시 URL을 확인해야 한다.

## 권고되는 다음 확인/수정

1. 새 파일 2~3장을 골라 저장할 때 Network의 요청 URL이 `POST /api/v1/me/photos/bundles`인지 확인한다. 요청 하나에 `files`가 반복 포함되어야 한다.
2. 그 직후 `GET /api/v1/me/photos/bundles` 응답에서 한 객체가 `id`를 가지고 `legacy:false`, `photos` 배열 길이가 2 이상인지 확인한다.
3. 만약 새 POST 이후에도 legacy라면 `attachBundle` 뒤 `PhotoRecord` 영속화 상태를 통합 테스트로 검증하고, 서버 SQL/응답을 확인하는 수정이 필요하다.
4. 사용자가 지금 보이는 기존 개별 사진도 묶고 싶다면, 자동 추측 이관이 아니라 사용자가 골라 `묶기`를 실행하는 별도 API/UI가 안전하다. 같은 날짜·장소만으로 자동 병합하면 서로 다른 여행 사진이 잘못 합쳐질 수 있다.

## 부가 발견

- `PhotoRecordAlbum.tsx`에 기존 단일 `PhotoUploadPanel` 구현과 `useUploadPhotoRecord`는 남아 있지만 현재 앨범 UI에서 렌더되는 호출은 없다. 직접 원인은 아니지만, 단일 업로드 경로를 계속 지원할지/미사용 코드를 제거할지는 이후 정리 대상이다.
