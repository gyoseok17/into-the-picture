+# M8.1 수상작 비교 공개 QA·보안 검토

## 범위

수상작 하나와 연결된 사진 비교 기록만 다른 사용자에게 공개한다. 앨범·지도·방문 기록 자체는 계속 본인 전용이다. 공개 기본값은 `PUBLIC`이다.

## 사전 계약·위험 점검 (2026-09-12)

### 현재 구조

- 비교 기록은 별도 `photo_comparison` 테이블이 아니라 `photo_record.contest_id` 연결로 표현된다.
- 현재 `GET /me/comparisons`, `/me/photos/{photoId}/file`은 모두 인증 및 소유자 검사를 전제로 하므로 공개 목록과 사진 전달에 그대로 재사용하면 안 된다.
- `UserPhotoDto`에는 촬영일, 장소명, 지도 지역/도시, 메모, 보관 상태 등 개인 앨범 속성이 포함된다. 공개 응답으로 사용하면 개인정보가 노출된다.

### 필수 계약

1. `PhotoRecord`에 비교 공개 상태만 별도 저장한다. 값은 `PUBLIC | PRIVATE`, 기존·새 레코드 기본값은 `PUBLIC`이다.
2. 공개 목록은 수상작 ID 기준으로만 조회한다. 공개 비교 전용 DTO에는 비교 ID, 수상작 요약, 공개 사진 URL, 표시 시각만 포함한다. 원본 파일명, 촬영일, 장소, 지도 좌표/코드, 메모, 사용자·앨범 식별자는 포함하지 않는다.
3. 공개 사진 URL은 소유자 전용 `/me/photos/{id}/file`가 아니라 공개 상태와 수상작 연결을 서버에서 매 요청 검증하는 별도 공개 endpoint를 사용한다.
4. 공개/비공개 전환은 반드시 현재 사용자 소유의 비교 기록에만 허용한다. 다른 사용자의 ID를 지정하면 404 또는 403이며 상태 변경이 일어나면 안 된다.
5. 비교 연결 해제, 비교 삭제, 사진 삭제 시 공개 목록과 공개 파일 endpoint에서 즉시 접근 불가해야 한다.
6. 공개 목록은 로그인 없이 볼 수 있어도 되지만, 공개 상태 변경·내 비교 관리 API는 인증을 유지한다.

### 차단 위험

- 공개 응답에 `UserPhotoDto`를 재사용하는 설계는 차단: 앨범 메모와 장소가 유출된다.
- 공개 이미지에 `/me/photos/{id}/file`를 노출하는 설계는 차단: 타인이 볼 수 없고, 권한 회피를 위해 endpoint를 느슨하게 만들면 개인 앨범 파일까지 위험해진다.
- 프런트 버튼만으로 공개 여부를 제한하는 방식은 차단: API 및 파일 endpoint에서 상태·수상작 연결을 검증해야 한다.

## 최종 검증 대기

백엔드·프런트 구현 수신 뒤 다음을 대조한다.

- 마이 비교 DTO와 공개 DTO의 필드 분리
- 공개 기본값·기존 데이터 마이그레이션
- 소유자 전환, 타인 전환 거부, 공개 목록/파일의 비공개 제외
- 연결 해제·삭제 뒤 공개 목록 및 파일 접근 차단
- 프런트 캐시 무효화, 전환 실패·중복 요청 UI
- backend test, frontend typecheck/build, diff check

## 구현 교차 검증 (2026-09-12)

### 계약과 권한

- `comparison_visibility`가 `photo_record`에 `PUBLIC | PRIVATE`, `NOT NULL DEFAULT 'PUBLIC'`으로 추가됐다. 기존 연결 기록도 migration 기본값으로 공개가 된다.
- 공개 목록은 `GET /api/v1/contests/{contestId}/comparisons`이며, 공개·활성(`archived_at is null`) 비교만 repository 조건으로 조회한다.
- 공개 DTO는 `id`, `photoUrl`, `createdAt`만 제공한다. `UserPhotoDto`와 분리되어 촬영일, 장소, 지도, 메모, 파일명, 소유자 식별자를 전달하지 않는다.
- 공개 파일은 `/api/v1/contests/{contestId}/comparisons/{comparisonId}/file` 전용 endpoint를 사용한다. 접근 전에 `id + contestId + PUBLIC + active`를 함께 조회하므로 다른 수상작 ID, 비공개, 삭제/연결 해제된 사진은 storage를 읽기 전에 404가 된다.
- 공개/비공개 전환은 `findOwnedRecord(userId, comparisonId)`를 거쳐 서버 소유자 검사를 한다. 비교 연결이 없는 레코드도 404 처리한다.
- 사진 교체 시 기존 `PRIVATE` 상태가 새 사진에도 유지되도록 보정됐다. 그렇지 않으면 교체가 의도치 않은 재공개가 되는 문제였다.

### 프런트 교차 검증

- 수상작 상세는 로그인 여부와 무관하게 공개 목록만 읽고, 자신의 비교 항목은 갤러리에서 제외한다.
- 내 비교 결과에는 공개/비공개 전환만 제공하며, 성공 뒤 내 비교 및 해당 수상작의 공개 목록 캐시를 함께 무효화한다.
- 처음 구현의 공개 URL은 `/contests/...`여서 raw `img`가 Vite 개발 서버 SPA fallback을 요청하는 차단 문제가 있었다. `/api/v1/contests/...`로 보정해 개발 proxy와 배포 API 경로가 일치한다.

### 검증

- `backend: .\\gradlew.bat test --tests com.intothepicture.domain.comparison.service.PhotoComparisonServiceTest` 통과.
  - 기본 PUBLIC, 소유자 전환, 타인 전환 거부, 공개 목록 repository 조건, 비공개/다른 수상작 파일 lookup의 storage 미접근, 비공개 교체 상태 보존을 확인한다.
- `frontend: npm run typecheck` 및 `npm run build` 통과.
- `git diff --check` 통과.
- Vite 795.52kB chunk 경고는 기존 성능 권고이며 이 기능의 차단 이슈는 아니다.

## 통합 판정

통과. 공개 범위가 비교 연결로 한정되고 개인 앨범 메타데이터와 소유자 전용 파일 경로가 분리되어 있다. 실제 브라우저 QA에서는 공개 비교 생성 후 수상작 상세의 타 계정/비로그인 표시, 비공개 전환 즉시 사라짐, 연결 해제·삭제 후 이미지 URL 직접 재요청 404를 확인한다.

## 공개 관리 전시 카드 재검토 (2026-09-13)

- `ComparisonExhibit`를 비교 결과 상세와 공개 관리 목록이 함께 사용한다. 수상작/내 사진 전시 규칙을 중복 복사하지 않았고, 관리 목록은 `showPersonalDetails=false`로 개인 메모·장소·촬영일을 불필요하게 반복 표시하지 않는다.
- 반응형은 넓은 화면에서 수상작·내 사진을 2열로, `md` 미만에서는 세로로 쌓는다. 카드와 상태 조작부는 `flex-wrap`·`min-w-0`을 사용해 좁은 화면에서 잘리지 않는다.
- 공개 상태는 읽을 수 있는 상태 텍스트와 Eye/EyeOff 아이콘으로 같이 표시한다. 변경 버튼은 현재 상태와 다음 행동을 `aria-label`로 제공하고, 진행 중 비활성화된다. 실패는 해당 카드 안에서 `role=alert`로 보인다.
- 공개 관리 route는 인증 가드 아래 `/me/comparisons`이며, 상태 전환은 기존 owner-only mutation·캐시 무효화 경로를 재사용한다.
- `npm run typecheck`, `npm run build`, `git diff --check` 통과. Vite 801.37kB chunk 경고만 비차단으로 남아 있다.

판정: 통과. 실제 브라우저에서는 320px 폭에서 카드 스택과 상태 버튼, 전환 실패 뒤 재시도, 공개/비공개 직후 수상작 공개 갤러리 반영을 마지막으로 확인한다.
