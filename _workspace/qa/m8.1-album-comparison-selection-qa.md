# M8.1 앨범 기반 사진 놓기 통합 QA 계약

작성일: 2026-09-03
상태: 구현 전 계약 검토 완료 · 구현 도착 후 최종 검증 대기

## 사용자 흐름 계약

| 진입 | 보여야 할 것 | 보여서는 안 될 것 |
| --- | --- | --- |
| 하단 `앨범` 탭 | 일반 앨범(스토리·맵·보관함·사진 추가)의 기존 흐름 | 수상작 고정, 비교 저장 버튼, 비교 전용 선택 상태 |
| 수상작 상세/마이의 `사진 놓기` CTA | `contestId`가 고정된 앨범 선택 모드와 비교 대상 수상작 맥락 | 다른 수상작으로 바꾸는 선택 UI |
| 이미 비교한 `contestId` | 기존 비교 결과를 즉시 열기 | 새 비교 생성 UI나 중복 POST |
| 새 사진 추가 | 업로드 성공 사진이 현재 선택 모드에 즉시 선택되고 해당 `contestId` 비교 생성에 사용됨 | 업로드 후 일반 앨범으로 이탈하거나 사진 ID를 잃는 흐름 |
| 비교 결과 | 비교에 연결된 내 사진과 수상작, 상세 진입·변경·삭제 동작 | 비교에 연결되지 않은 앨범 전체 사진의 결과 영역 노출 |

## 코드·계약 점검 항목

- [ ] `/me/album`은 query 없이 일반 모드로 시작하며, 비교 관련 상태가 URL·저장소·전역 상태에 남아 일반 앨범을 오염시키지 않는다.
- [ ] 비교 진입은 `contestId`를 URL 또는 명시적 props로만 전달한다. 숫자가 아니거나 존재하지 않는 ID는 안전한 오류/복귀 상태를 보인다.
- [ ] 비교 생성 전에 사용자 소유의 활성 `PhotoRecord`만 선택할 수 있다. 보관 사진, 다른 사용자의 사진, 이미 다른 비교에 사용 중인 사진의 허용 여부는 서버 계약과 UI가 일치한다.
- [ ] 새 사진 업로드 mutation 성공값의 ID가 선택 상태와 비교 생성 payload에 그대로 연결된다. 실패·중복 클릭·취소에서는 선택 상태와 목록이 깨지지 않는다.
- [ ] 기존 비교 탐색은 사용자별 `contestId` 기준이며, 발견 시 결과를 열고 생성 mutation을 호출하지 않는다.
- [ ] 비교 연결 사진만 표시하는 영역은 비교 API의 `userPhoto`를 기준으로 하고, 앨범 목록 필터와 혼동하지 않는다.
- [ ] 변경은 소유 사진으로만 교체하고 비교/사진 캐시를 갱신한다. 삭제는 결과만 삭제와 사진까지 삭제를 명확히 구분한다.
- [ ] 비로그인 사용자는 앨범·비교 데이터나 업로드 UI를 잠깐이라도 보지 않고 로그인 흐름으로 이동한다.

## 수동 통합 체크리스트

- [ ] 로그인 후 하단 앨범 탭에서 기존 스토리, 맵, 보관함, 사진 추가가 이전과 동일하게 동작한다.
- [ ] 일반 앨범에서 사진 추가·수정·보관·복원 후 비교 관련 문구·버튼·선택 상태가 나타나지 않는다.
- [ ] 즐겨찾기 수상작 A의 상세와 마이 CTA가 같은 `contestId=A` 앨범 선택 모드로 진입한다.
- [ ] A에 기존 비교가 있으면 즉시 결과가 열리고 Network에 비교 생성 POST가 없다.
- [ ] A에 기존 비교가 없으면 내 사진 선택 후 저장할 수 있고, 새 사진을 추가해도 A가 유지된 채 새 사진이 선택되어 비교로 연결된다.
- [ ] 결과 화면에는 A와 연결 사진만 표시되며, 상세 진입·사진 변경·결과만 삭제·사진까지 삭제가 각각 정상 동작한다.
- [ ] 비교 결과만 삭제하면 원본 사진은 일반 앨범에 남고, 사진까지 삭제하면 서버/앨범/결과 캐시가 함께 갱신된다.
- [ ] 직접 URL의 비즐겨찾기/잘못된 `contestId`는 생성할 수 없고 사용자가 이해할 수 있는 안내가 보인다.
- [ ] 비로그인 상태에서 하단 앨범, 수상작 CTA, 직접 비교 URL 모두 보호 흐름이 일관되게 작동한다.
- [ ] 모바일 320px 및 일반 폭에서 선택 모드 헤더, 업로드 시트, 결과/삭제 dialog가 하단 내비게이션에 가려지지 않고 닫기·뒤로가기가 자연스럽다.

## 차단 기준

- 일반 앨범이 비교 전용 상태로 열린다.
- 기존 비교가 있는데 새 비교 POST가 발생한다.
- 업로드한 새 사진이 선택/비교 생성에 연결되지 않거나 다른 수상작에 연결된다.
- 비교와 무관한 사진이 결과 영역에 섞이거나, 삭제 범위가 사용자 선택과 다르다.
- 비로그인·잘못된 URL에서 개인 사진 또는 보호된 UI가 노출된다.
## 최종 소스·타입 검증 (2026-09-03)

### 통과

- 하단 내비게이션의 앨범은 `/me/album`, 라우터는 `RequireAuth` 아래의 `AlbumPage`로 연결된다.
- 일반 `/me/album`에는 `contestId`가 없어 `AlbumComparisonPicker`가 렌더링되지 않는다. 스토리·맵·보관함·사진 추가는 기존 `PhotoRecordAlbum` 흐름을 유지한다.
- 수상작 상세와 마이의 신규 CTA는 `/me/album?contestId=<id>`로 통일됐다. 해당 수상작의 기존 비교를 찾으면 앨범에서 `/compare?contestId=<id>`로 교체 이동하며 생성 mutation을 호출하지 않는다.
- 선택 모드는 앨범 묶음을 평탄화한 개별 `PhotoRecord` ID를 생성 payload에 전달한다. 새 사진은 업로드 성공 응답 ID를 그대로 선택·생성에 연결하고, 성공 후 동일 `contestId`의 비교 결과로 이동한다.
- 비교 연결 표시는 `comparison.userPhoto.id`로 만든 색인을 사용한다. 스토리 라이트박스는 현재 선택된 사진 ID의 비교만 `PhotoComparisonLinks`로 표시하고, 각 링크는 `/compare?contestId=<해당 수상작>`으로 결과를 연다. 묶음의 다른 사진 연결이 현재 사진에 섞이지 않는다.
- 비교 타입은 서버 `displayMode`를 `PhotoDisplayMode`와 공유한다. `BUNDLE_START_FALLBACK`은 프런트 타입과 백엔드 enum에 모두 있고, 백엔드는 EXIF·수동 날짜가 없을 때만 묶음 시작일로 설정한다.
- `node node_modules/typescript/bin/tsc -b` 통과했고 `git diff --check`에 공백 오류는 없었다(작업 트리의 LF/CRLF 경고만 출력).

### 실행 환경으로 분리한 미검증 항목

- `npm.cmd run build`의 Vite 단계는 현재 샌드박스가 프로젝트 상위 디렉터리를 읽지 못해 실패했다. 오류는 `Cannot read directory "../../..": Access is denied`, 이어서 `Could not resolve .../frontend/vite.config.ts`이며 소스·타입 오류가 아니다. TypeScript 단독 빌드는 통과했다.
- Gradle 대상 테스트는 격리 환경에 Gradle 8.14.3 배포본이 없어 다운로드를 시도하다 네트워크 제한(`java.net.SocketException: Permission denied: getsockopt`)으로 실행되지 않았다. `UserPhotoServiceTakenAtTest`에는 `BUNDLE_START_FALLBACK` 기대값이 존재하는 것은 소스로 확인했다.

### 최종 판정

**차단 이슈 없음. 코드·타입·계약 기준 통과.** 실제 로그인 계정에서 업로드·삭제·모바일 시트의 체감 동작은 커밋 전 수동 확인 항목으로 유지한다.
