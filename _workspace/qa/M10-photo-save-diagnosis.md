# M10 사진 저장 실패 진단 (QA, 2026-09-20)

## 범위

- 코드 수정 없이 앨범 사진 묶음 저장 경로를 프런트 multipart 요청, 인증, 백엔드 유효성 검사, DB, S3 저장소 순서로 점검했다.
- 시크릿·토큰·개인 파일명은 기록하지 않았다.

## 현재 확인 결과

1. **백엔드 프로세스는 현재 8080 포트를 수신 중이다.** 인증 없이 `GET /api/v1/me/photos/bundles`를 호출하면 `401`이므로, 적어도 보안 필터와 HTTP 서버는 살아 있다.
2. **DB 연결 정보의 네트워크 도달성은 현재 확인된다.** 현재 설정된 Supabase pooler 호스트는 DNS 해석과 TCP 5432 연결이 성공했다. 과거 로그에 있던 `UnknownHostException`은 9월 7일 기록이라 이번 실패의 직접 근거로 사용할 수 없다.
3. **묶음 저장 요청 계약은 일치한다.** 프런트는 `POST /me/photos/bundles`에 `files` 반복 multipart 필드를 보내고, 컨트롤러는 같은 이름의 `List<MultipartFile>`을 받는다. 수동 촬영일이 하나라도 있으면 프런트가 모든 파일 위치에 값 또는 `__AUTO__`를 넣고, 백엔드도 같은 자리 수를 요구한다.
4. **최근 지역 규칙 때문에 요청 전에 멈출 수 있다.** `useBatchPhotoUpload`은 시·군까지 선택되지 않으면 `pendingCount`를 0으로 만들고 `uploadPending()`도 조용히 반환한다. 이 경우 네트워크 요청 자체가 없다. 지역 선택이 빠졌을 때 사용자에게 별도 오류 메시지를 보여 주지는 않는다.
5. **서버 실패 사유도 현재 UI에서 소실된다.** `useBatchPhotoUpload.uploadPending()`의 `catch`는 응답 오류를 표시하지 않고 항목 상태만 `failed`로 바꾼다. 따라서 400(촬영일/지역), 401(세션), 500(DB/S3)을 사용자가 구별할 수 없다.
6. **S3는 별도 실패 지점이다.** 현재 저장소 설정은 `s3`이며 `UserPhotoUploadService`가 파일을 먼저 저장하고 DB 레코드를 만든다. IAM 권한·자격 증명·버킷 접근 실패면 서버는 `Failed to save the photo.` 형태의 500을 반환한다. 현재 실행 프로세스의 실제 S3 자격 증명 성공 여부는 안전상 확인하지 않았고, 실패 요청 로그가 없으므로 단정할 수 없다.

## 실패 유형을 가르는 브라우저 확인 항목

DevTools Network에서 사진 저장 직후 아래 요청을 고른다.

- 요청이 **없음**: 지역을 시·군까지 선택하지 않아 프런트가 저장을 막은 경우다.
- `POST /api/v1/me/photos/bundles`의 **400**: Response의 `message`를 확인한다. 촬영일 누락, 종료일 역전, 수동 촬영일 개수/형식, 지역 코드 불일치 중 하나다.
- **401**: Request Headers에 `Authorization: Bearer ...`가 있는지와 로그인 직후 세션이 유지되는지 확인한다.
- **500**: Response body와 백엔드 실행 터미널의 같은 시각 첫 `Caused by:`를 확인한다. DB 연결 실패와 S3 `AccessDenied`/자격 증명 실패는 여기서 구분된다.
- 요청 Payload: `files`가 선택한 개수만큼 있고, 수동 촬영일이 한 장이라도 설정되었을 때 `manualTakenAts`도 같은 개수인지 확인한다.

## 판정과 권고

- 현재 확보된 근거만으로는 DB/S3 장애라고 단정할 수 없다. 가장 먼저 확인할 것은 **실제 POST가 발생했는지**다. 최근 지역 선택 필수화 때문에 요청 자체가 생기지 않는 경우가 있다.
- 단, 서버 오류를 숨기는 현재 프런트 처리와 지역 미선택 안내 부재는 진단성을 낮춘다. 실제 원인 확인 뒤, 다음 수정 범위에서 서버 응답 메시지와 지역 미선택 안내를 노출하는 것이 적절하다.
