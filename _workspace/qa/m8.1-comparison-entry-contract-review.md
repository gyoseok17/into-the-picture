# M8.1 사진 놓기 진입 경로 서버 계약 검토

## 결론

백엔드 변경은 필요하지 않다. 새 비교 생성 허용 여부는 화면의 진입 위치가 아니라 요청 사용자·수상작·사진 기록의 서버 상태로 판정해야 한다. 상세와 마이에서 `/compare?contestId={id}`로 진입해 같은 `POST /api/v1/me/comparisons`를 호출하는 구조는 현재 계약과 일치한다.

## 대조 결과

- `POST /me/comparisons`는 현재 사용자가 소유한 `PhotoRecord`만 비교 사진으로 받는다. 업로드 묶음 자체를 비교 원본으로 받지 않는다.
- 수상작이 사용자의 `CONTEST` 즐겨찾기에 있어야 생성되며, 아니면 `403 FORBIDDEN`이다.
- 같은 사용자·수상작의 기록이 이미 있으면 `409 CONFLICT`이고 기존 기록을 덮어쓰지 않는다.
- 기존 기록 변경은 `PATCH /me/comparisons/{comparisonId}`를 사용하므로, 결과 목록 중심의 사진 놓기 탭에는 생성 API가 필요 없다.

## 프런트 회귀 위험

- 현재 점검 시점의 `ComparePage`에는 `contestId`가 없는 경우에도 새 사진 놓기 composer를 여는 버튼과 `useCreateComparison` 호출 경로가 남아 있다. 탭을 결과 목록 전용으로 바꾸는 작업에서 이 경로를 제거하거나 상세·마이에서 전달된 `contestId`가 있을 때만 composer를 렌더링해야 한다.
- 상세·마이의 새 비교 링크는 즐겨찾기 여부와 기존 비교 부재를 화면에서 먼저 확인하고 있지만, 서버의 403/409 처리도 유지해야 한다. 다른 탭·오래 열린 화면·직접 요청은 이 UI 조건을 우회할 수 있다.
- 409를 받은 뒤 새 기록을 만들려고 재시도하지 말고, 비교 목록을 다시 조회하여 기존 결과/수정 흐름으로 안내해야 한다.

## 판정

API·권한·중복 제약은 그대로 유지한다. 이번 UI 변경은 프런트의 생성 진입점과 오류 안내를 정리하는 범위이며, 서버 라우트나 DTO 추가는 필요 없다.
