# M8.1 `.env` 설정 전환 QA·보안 사전 검토

## 점검 범위

- `backend/src/main/resources/application.yml`
- `backend/src/main/resources/application-local.yml`
- 루트 `.env`의 **키 이름만** 확인 (값은 열람·기록하지 않음)
- 루트/백엔드 `.gitignore`

## 현재 확인 결과

1. 루트 `.env`는 Git 추적 대상이 아니고, 루트 `.gitignore`에서 제외된다.
2. DB·JWT 관련 키는 `.env`에 존재하지만, Spring 설정에 `spring.config.import` 또는 dotenv 라이브러리가 없다. 따라서 현 상태에서는 `.env` 값이 자동 주입되지 않는다.
3. `application-local.yml`에는 DB host/port/name의 기본값과 JWT 공개 fallback 값이 있다. 사용자가 요구한 “YAML 기본값 대신 `.env` 참조”와 일치하지 않는다.
4. `.env`에는 `DB_HOST`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET`은 있으나 `DB_PORT`, `DB_NAME`은 없다. YAML의 기본값을 완전히 제거하려면 이 두 키도 `.env`에 추가되어야 한다. 값은 이 문서에 기록하지 않는다.

## 안전한 변경 조건

- local 프로필에서 `.env`를 Spring Config Data로 읽는다. 확장자 없는 파일은 properties 힌트(`.env[.properties]`)가 필요하다.
- 실제 파일 위치가 루트라면 backend 실행 기준의 상대 경로가 일관되게 동작하는지 검증한다. 장기적으로는 backend 전용 `.env` 위치를 정하고 `.env.example`에는 키 이름만 제공하는 편이 이식성이 더 좋다.
- DB와 JWT의 모든 필수 값은 빈 fallback 없이 `${KEY}`로 참조해 누락 시 기동 단계에서 명확히 실패해야 한다.
- JWT의 최소 32-byte raw UTF-8 검증은 `JwtService`에 그대로 남긴다. `.env` 주입은 검증을 대체하지 않는다.
- `.env`, 로그, development-log, `_workspace` 어디에도 실제 값·연결 URL·토큰을 기록하지 않는다.
- `local`에만 파일 import를 두고, 배포 프로필은 플랫폼 환경변수/시크릿 저장소를 계속 사용한다.

## 검증 게이트

1. `.env`를 읽는 local 기동에서 DB/JWT placeholder가 해석되는지 확인한다.
2. `JWT_SECRET`이 짧으면 기존의 32-byte 예외가 유지되는지 확인한다.
3. `.env` 또는 필수 키 하나가 빠졌을 때, fallback으로 접속하지 않고 어떤 키가 부족한지 확인 가능한 기동 오류가 나는지 확인한다.
4. `git status --ignored`와 `git ls-files`로 `.env`가 추적되지 않는지 재확인한다.
5. 운영 프로필에서 local `.env` import가 적용되지 않는지 확인한다.

## 사전 판정

**조건부 통과.** `.env` import 추가, YAML fallback 제거, 누락된 `DB_PORT`·`DB_NAME` 키 보완 후 최종 기동 검증이 필요하다.

## 변경 도착 뒤 중간 판정 (2026-09-07)

- 반영 확인: local 설정에 루트 `.env` properties import가 추가됐고 DB URL·JWT의 YAML fallback은 제거됐다.
- 차단: import가 `optional:`이어서 `.env` 자체가 누락돼도 즉시 명확히 실패하지 않는다. 또한 확인 시점에도 `.env`의 `DB_PORT`, `DB_NAME` 키는 없다. 현재 `${DB_PORT}`, `${DB_NAME}`는 해석 불가이므로 데이터소스 설정 단계에서 기동이 실패한다.
- 최종 판정 보류: 두 DB 키를 비밀값을 노출하지 않는 방식으로 보완하고, 필요한 local import로 변경한 다음 실제 `bootRun` 결과를 다시 확인해야 한다.
