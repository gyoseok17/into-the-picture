# M8.1 즐겨찾기 수상작 → 사진 놓기 진입 QA

작성일: 2026-09-01
상태: 구현 전 경로·권한 점검 및 수동 QA 체크리스트

## 현재 경로 대조

- `/me`의 저장한 수상작 목록과 `/compare`는 모두 로그인 필수 라우트다.
- `/compare`는 현재 query parameter로 수상작을 선택해 새 사진 놓기 composer를 열 수 있는 구조다. 즐겨찾기 CTA는 이 deep link를 사용해야 하며, 목록/상세에서 별도 비교 생성 상태를 만들면 안 된다.
- 비교 결과는 `PhotoRecord.contest` 연결로 표현되며, 한 사진 record는 하나의 수상작 비교만 가질 수 있다.
- 현재 서버의 `POST /me/comparisons`는 소유한 사진·수상작 존재·사진 중복만 확인하고 **수상작 즐겨찾기 여부를 확인하지 않는다**. UI에서 CTA를 숨겨도 API 직접 호출로 우회할 수 있으므로, 즐겨찾기 한 수상작만 새 비교를 만들 수 있다는 정책이면 서버 검증이 필요하다.

## 목표 계약

- 비교 시작 CTA는 현재 사용자가 즐겨찾기한 수상작에서만 노출한다. 비즐겨찾기 수상작의 상세·직접 URL·목록에는 CTA가 없다.
- deep link는 `/compare?contestId=<id>`처럼 수상작 ID만 전달한다. 사용자 ID·favorite ID·사진 URL을 query로 넘기지 않는다.
- `/compare` 진입 시 해당 수상작으로 이미 만든 비교가 있으면 새 composer를 열거나 중복 record를 만들지 않고 기존 결과를 열어 사진 교체·삭제 등 기존 편집 흐름을 제공한다.
- 새 비교 생성 요청은 서버에서 `userId + contestId` 즐겨찾기 존재를 확인한다. 비즐겨찾기는 403/프로젝트 표준 권한 오류이며 사진 record·contest 연결을 변경하지 않는다.
- 비교를 이미 만든 뒤 즐겨찾기를 해제해도 기존 비교는 유지·조회·사진 교체·삭제할 수 있다. 단, 해제 상태에서 같은 수상작으로 **새** 비교를 추가 생성할 수는 없다.

## 수동 QA 체크리스트

### CTA와 deep link

- [ ] 비로그인: 수상작 상세에서 새 비교 CTA가 보이지 않거나 로그인 흐름으로만 안내되며, `/compare` 직접 진입은 RequireAuth로 차단된다.
- [ ] 로그인·비즐겨찾기: 상세/마이 저장목록에 비교 시작 CTA가 없고, `/compare?contestId=<비즐겨찾기>` 직접 진입도 새 composer를 열지 않는다. 사용자에게 저장 후 사용 가능하다는 다음 행동이 보인다.
- [ ] 즐겨찾기 직후: 낙관적 상태와 서버 재조회 뒤 CTA가 일관되게 보이며, CTA 클릭은 정확한 `contestId`로 `/compare`에 진입한다.
- [ ] 다른 사용자 즐겨찾기/즐겨찾기 ID를 URL로 조작해도 자기 계정의 favorite 권한만 적용된다.

### 신규·기존 비교

- [ ] 즐겨찾기 A에서 비교가 없는 상태: deep link가 A를 미리 선택하고 사진 고르기/업로드 후 비교 하나만 생성한다.
- [ ] 동일 A deep link를 다시 열기: 기존 비교 결과가 즉시 열리고 composer/POST가 자동 실행되지 않는다.
- [ ] A에 연결된 사진을 교체: 기존 비교 ID/수상작은 유지되고 이전 사진은 비교 연결만 해제된다.
- [ ] 새 사진으로 같은 A에 비교하려 할 때: 정책상 하나의 수상작당 하나의 비교라면 기존 비교 열기만 제공하고 중복 생성이 없다. 여러 비교를 허용할 정책이라면 이 항목은 별도 데이터 모델·목록 기준이 필요하므로 이번 계약과 혼용하지 않는다.
- [ ] 비교 삭제: 수상작 A는 그대로 즐겨찾기 상태이며 deep link 재진입 시 새 composer를 열 수 있다.

### 즐겨찾기 해제 이후

- [ ] A 비교 생성 후 마이/상세에서 A 즐겨찾기 해제: 저장 목록 CTA는 사라지지만 기존 `/compare?contestId=A` 결과는 열린다.
- [ ] 해제 뒤 기존 비교 사진 교체·비교 삭제: 정상 동작한다. 기존 연결에 대해 즐겨찾기 재검증으로 403을 내면 안 된다.
- [ ] 해제 뒤 비교를 삭제한 다음 `/compare?contestId=A` 재진입: 새 비교는 시작할 수 없고, 서버 POST도 거부한다.

### 서버·오류·모바일

- [ ] API 직접 POST: 비즐겨찾기 contest ID는 서버가 거부하며 record의 `contest_id`, `display_mode`, `contest_linked_at`가 변하지 않는다.
- [ ] 다른 사용자의 photo record ID, 없는 contest ID, 이미 다른 비교에 사용 중인 photo record ID는 기존 소유권/404/409 규칙을 유지한다.
- [ ] favorite 해제 요청과 비교 POST 경쟁 상황에서 서버는 최종 트랜잭션 상태를 기준으로 하나만 성공시키며, UI는 실패를 비교 생성 성공처럼 보이지 않는다.
- [ ] 모바일 320px/일반 폭: deep link 이후 composer 또는 기존 결과가 하단 네비게이션에 가려지지 않고, 뒤로가기는 수상작/마이의 원래 위치로 자연스럽게 돌아간다.
- [ ] 키보드·스크린리더: CTA의 수상작 이름·행동이 접근 가능한 이름에 포함되고, 기존 결과를 여는 경우에도 "새 비교"로 오해시키지 않는다.

## 차단 기준

- 비즐겨찾기 사용자가 API를 직접 호출해 새 비교를 만들 수 있음.
- 기존 비교가 있는 수상작으로 deep link 진입할 때 중복 비교가 생성됨.
- 즐겨찾기를 해제했다는 이유만으로 기존 비교의 조회·교체·삭제가 막힘.
- deep link의 contest ID와 실제 선택/생성 수상작이 다름.
