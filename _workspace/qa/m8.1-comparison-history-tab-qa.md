# M8.1 사진 놓기 탭: 비교 기록 전용 통합 QA

작성일: 2026-09-03
상태: 구현 전 계약 대조 완료, 최종 통합 검증 대기

## 전환 계약

- `/compare` 탭은 기존 사진 놓기 **기록 조회·열기·수정·삭제 전용**이다. 탭 내부의 새 비교 composer, 사진 업로드, 수상작/사진 선택기는 노출하지 않는다.
- 새 비교의 유일한 진입점은 즐겨찾기한 수상작의 상세와 마이 저장 목록 CTA다. 진입 URL은 `/compare?contestId=<id>`다.
- deep link 대상에 기존 비교가 있으면 그 결과를 바로 연다. 대상이 즐겨찾기지만 비교가 없으면 새 비교 작성 흐름을 연다. 비즐겨찾기 또는 잘못된 ID는 새 composer를 열지 않는다.
- 비교 결과의 수정(사진 교체)·삭제는 `/compare` 기록 화면에서 기존 API/권한 규칙대로 제공한다. 즐겨찾기 해제 뒤의 기존 비교도 계속 관리 가능하다.

## 현재 코드와의 차이

- 현재 `ComparePage`에는 탭에서 새 composer를 여는 버튼, 선택 패널, 사진 업로드/고르기 흐름이 존재한다. 전환 구현에서 이 경로를 제거해야 한다.
- `ContestDetailPage`와 마이의 저장 수상작은 `/compare?contestId` deep link를 이미 사용하므로, 새 진입 경로를 별도 상태/라우트로 만들 필요가 없다.
- 기존 `ComparisonView`의 사진 교체·결과 삭제/사진도 삭제 동작은 기록 전용 탭에 남아야 한다.

## 수동 QA 체크리스트

- [ ] 비로그인 `/compare`: RequireAuth로 로그인 흐름으로 이동하며 비교 목록·업로드 UI가 노출되지 않는다.
- [ ] 로그인·비교 없음 `/compare`: "아직 사진 놓기 기록이 없어요" 빈 상태와 수상작에서 시작하는 안내만 보이고 새 비교 작성 버튼/사진 업로드/수상작 선택기는 없다.
- [ ] 로그인·기존 비교 N개: 각 기록 카드에서 결과를 열 수 있고, 카드의 수상작·내 사진 상태가 정확하다. 탭 안에 새 비교 composer가 없다.
- [ ] 기존 결과 열기: 사진 교체·결과만 삭제·사진도 삭제가 기존과 동일하게 동작하고 query cache/카드·빈 상태가 갱신된다.
- [ ] 상세의 즐겨찾기 수상작 CTA: 비교 없음이면 `/compare?contestId=A`로 새 작성 흐름 진입, 비교 있음이면 같은 URL로 기존 결과가 열린다. 중복 POST는 없다.
- [ ] 마이 저장 수상작 CTA/썸네일: 상세과 동일한 contestId·동작이며 비교 있음/없음 상태가 일치한다.
- [ ] 비즐겨찾기 `/compare?contestId=A`: 새 작성 흐름을 열지 않고 안내한다. API 직접 POST도 서버가 거부한다.
- [ ] 비교 생성 뒤 즐겨찾기 해제: 탭의 기존 기록은 열기·교체·삭제 가능하며, 삭제 후 같은 deep link는 새 작성 불가 안내가 나온다.
- [ ] 모바일 320px: 기록 카드·결과 modal·수정/삭제 시트가 하단 내비게이션과 겹치지 않고, 탭/뒤로가기 후 스크롤이 자연스럽다.
- [ ] 접근성: 빈 상태의 다음 행동은 수상작 탐색으로 명확하고, 결과 카드·수정·삭제의 accessible name과 modal Escape/포커스 복귀가 유지된다.

## 최종 판정 게이트

- [ ] `ComparePage`에서 탭 단독 새 비교 생성 경로 제거 확인
- [ ] 상세·마이 deep link와 existing comparison 중복 방지 확인
- [ ] 비즐겨찾기 서버 거부·기존 비교 관리 권한 교차 확인
- [ ] 프런트 build 및 위 핵심 흐름 수동 QA 통과

탭 안에서 새 비교가 다시 생성되거나, deep link가 기존 비교를 중복 생성하거나, 기존 기록 관리가 깨지면 **차단**이다.

## 최종 코드·빌드 대조 (2026-09-03)

### 통과

- `/compare` 단독 진입에는 수상작 선택 패널·독립 새 비교 버튼·standalone composer가 없다. 비교 기록 목록 또는 수상작 탐색 CTA만 렌더한다.
- `/compare?contestId=<id>`는 이미 저장된 비교를 `existingComparison`으로 찾아 자동으로 결과 modal을 연다. 기존 비교가 없을 때만 contest ID가 고정된 내 사진 선택 composer를 연다.
- `ComparisonView`에는 사진 변경, 결과만 삭제, 사진도 삭제 경로가 남아 있다. 비교 mutation은 기존 comparisons/user-photos cache invalidation을 사용한다.
- 마이·상세는 같은 deep link를 유지하고, 비교가 있으면 `ContestComparisonEntry`로 기존 결과 진입, 없으면 텍스트 CTA를 보인다.
- 서버 `PhotoComparisonService.create`는 즐겨찾기 소유 여부를 403으로 검증하고 사용자·수상작당 기존 비교가 있으면 409으로 차단한다. 비교 교체·삭제에는 즐겨찾기 재검증을 하지 않아 해제 뒤 기존 기록 관리를 보존한다.
- `frontend npm run build`: 통과. Vite 500 kB chunk 경고만 발생했다.
- `git diff --check`: 오류 없음. 작업 트리의 기존 LF→CRLF 경고만 발생했다.

### 수동 확인 필요

- 실제 로그인 계정에서 `/compare` 빈 상태의 수상작 탐색 CTA, 유효한 deep link 신규 작성, 기존 결과 자동 열기, 사진 변경/두 삭제 선택을 확인한다.
- 비즐겨찾기 contestId를 수동으로 넣어 POST가 403일 때 composer에 사용자가 이해할 수 있는 오류 안내가 보이는지 확인한다. 서버 차단은 코드상 확인됐지만 현재 ComparePage의 생성 실패 노출은 수동 확인이 필요하다.
- 모바일 320px에서 결과 modal·사진 선택 dialog·삭제 확인 dialog의 하단 내비게이션 겹침과 Escape/배경 닫기를 확인한다.

### 통합 판정

**코드·빌드 기준 통과, 수동 QA 대기.** 독립 탭의 신규 수상작 선택 경로는 제거됐고, deep link·기존 결과·관리·서버 중복/즐겨찾기 경계가 계약과 일치한다. 위 수동 항목에서 오류 안내 또는 모바일 modal 문제가 확인되면 커밋 전 보완한다.
## ComparePage 책임 단위 리팩터링 재검증 (2026-09-03)

### 교차 확인 결과

- 레거시 standalone composer 상태·컴포넌트인 `isComposerOpen`, `SelectionPanel`은 코드베이스에 남아 있지 않다.
- `/compare` 단독 진입은 `ComparisonHistory`와 빈 상태의 수상작 탐색 CTA만 렌더링한다. `contestId`가 없으면 사진 선택·업로드·생성 composer가 열리지 않는다.
- `/compare?contestId=<id>`는 목록을 받은 뒤 기존 결과를 `existingComparison`으로 찾아 자동 선택한다. 기존 결과가 없을 때만 해당 수상작 ID가 고정된 사진 선택 composer를 표시한다.
- 사진 교체는 `useReplaceComparisonPhoto`에 comparison ID와 새 사진 ID를 전달하고, 성공 시 선택 창을 닫는다. 삭제는 결과만 삭제(`deletePhoto: false`)와 사진까지 삭제(`deletePhoto: true`)를 명확히 분리해 기존 계약을 보존한다.
- 페이지 내부는 기록 목록, 사진 선택, 결과 보기, 삭제 확인의 책임 단위 컴포넌트로 구분되어 있으며, 비교 생성은 deep link 전용 분기로 한정돼 있다.

### 빌드·변경 점검

- `frontend npm run build` 통과: TypeScript 빌드와 Vite 프로덕션 번들이 완료됐다.
- Vite의 초기 번들 500 kB 초과 경고만 발생했으며, 이번 리팩터링의 실패나 타입 오류는 아니다.
- `git diff --check`에서 공백 오류는 없었다. 작업 트리의 기존 LF/CRLF 경고만 출력됐다.

### 통합 판정

**리팩터링 후 코드·빌드 기준 통과, 실제 계정 수동 QA 대기.** 이전 최종 QA의 수동 확인 항목(빈 기록, 신규·기존 deep link, 사진 교체, 두 삭제 선택지, 비즐겨찾기 403 안내, 모바일 dialog)은 그대로 유효하다.
