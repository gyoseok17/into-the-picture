# M8.1 스토리 사진 묶음 표시 진단

## 결론

스토리 카드 렌더링은 `PhotoRecordBundle` 하나당 카드 하나를 만드는 구조로 이미 묶음 표시를 지원한다. 현재 사용자가 보는 최근 3장은 DB에서 모두 `bundle_id = NULL`인 기존 개별 기록이므로, 정상적으로 각각 카드로 보인다. 화면 그룹핑 문제가 아니다.

## 확인 근거

- `PhotoRecordAlbum.tsx`는 `/me/photos/bundles`의 응답을 `groupBundles()`에 전달하고, 그 결과의 `bundle`마다 `PhotoRecordBundleCard` 하나를 렌더링한다.
- 카드 내부 사진 수 표시는 `bundle.photos.length > 1`일 때만 나타난다. 즉 API가 하나의 bundle에 3장을 반환하면 카드 1개 + `사진 3장`으로 표시된다.
- 2026-08-28 22:45에 생성된 최근 `photo_record` 3건(id 10, 11, 12)은 모두 `bundle_id = NULL`이다. `photo_record_bundle`에는 행이 없다. 따라서 `/me/photos/bundles` 조회 시 legacy one-photo bundle 3개로 변환되어 각자 보이는 것이 서비스 코드상 예상된 결과다.

## 원인 범위

현재 DB의 최근 기록은 `POST /me/photos` 단건 경로로 생성됐다. 새 다중 업로드 패널의 소스는 `POST /me/photos/bundles`를 한 번 호출하도록 되어 있으므로, 다음 중 하나를 실제 요청에서 확인해야 한다.

1. 사용자가 앨범 지도 사진 추가가 아닌 비교 화면 등의 기존 단건 업로드 흐름을 사용했다.
2. 브라우저가 변경 전 프런트 번들을 계속 사용했다.
3. 해당 테스트 시점에 새 다중 업로드 패널과 연결되지 않은 화면 경로가 남아 있다.

## 수정·검증 제안

1. 사진을 여러 장 고른 뒤 Network에서 요청이 `POST /api/v1/me/photos/bundles` 한 건인지 확인한다. `POST /api/v1/me/photos`가 여러 건이면 호출 경로 문제다.
2. 테스트로 새 묶음 2~3장을 올린 뒤 DB/API 응답에 `bundleId`/`id`가 하나로 생성되고 `photos` 배열 길이가 2 이상인지 확인한다.
3. 기존 `bundle_id = NULL` 기록을 임의로 자동 병합하지 않는다. 서로 다른 시점에 올린 사진을 잘못 합칠 위험이 있으므로, 필요하면 사용자가 선택하는 별도 '묶음 만들기' 기능으로 처리한다.

## 영향

- 기존 개별 사진 데이터 손실 없음.
- 스토리 렌더 코드 수정은 현재 근거상 불필요.
- 실제 단건 업로드 경로가 앨범의 사진 추가로 남아 있으면 그 경로를 새 묶음 업로드로 통일해야 한다.
