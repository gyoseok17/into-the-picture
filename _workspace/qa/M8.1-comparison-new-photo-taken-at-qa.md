# M8.1 사진 놓기 새 사진 촬영일 QA

## 판정

차단 이슈. 새 사진을 사진 놓기에 바로 추가하는 경로가 촬영일 계약을 충족하지 못한다.

## 원인과 계약 대조

- `AlbumComparisonPicker`는 새 파일을 `useUploadPhotoRecord({ file })`로 보낸다.
- 이 훅은 `POST /api/v1/me/photos`를 호출하며 현재 `file` 외의 `takenAt`을 보내지 않는다.
- 같은 레거시 업로드 경로를 쓰는 비교 상세의 `uploadUserPhoto(file)`도 `takenAt`을 보내지 않는다.
- 서버 `UserPhotoService.resolveTakenAt`은 단일 사진에서 요청 `takenAt` 또는 서버 EXIF 중 하나가 있어야 한다. 둘 다 없으면 `400 INVALID_REQUEST`와 "촬영일을 확인할 수 없습니다"를 반환한다.
- 따라서 EXIF가 없는 새 사진은 현재 사용자에게 촬영일을 입력할 기회 없이 실패한다. 이는 공통 사진 추가 패널 계약의 "EXIF를 읽지 못하면 촬영일 필수" 규칙과 다르다.

## 회귀 범위

| 흐름 | 현재 결과 | 필요한 보장 |
| --- | --- | --- |
| 새 사진, EXIF 촬영일 있음 | 서버 EXIF로 저장 가능 | 촬영일을 확인·수정할 수 있고, 저장값이 비교 사진에도 유지됨 |
| 새 사진, EXIF 촬영일 없음 | 입력 없이 400 실패 | 촬영일 선택을 필수로 하고 `takenAt`을 multipart로 전송 |
| 새 사진, 수동 촬영일 지정 | 현재 UI 경로 없음 | 날짜를 ISO local datetime으로 전달하여 서버 수동값으로 저장 |
| 기존 앨범 사진 선택 | 정상, 재업로드 없음 | 기존 `PhotoRecord`를 그대로 비교에 연결하고 촬영일을 다시 요구하지 않음 |
| 서버 검증 | EXIF/요청일 모두 없으면 거부 | UI 우회 요청도 계속 거부하여 기록 데이터의 촬영일 보장 |

## 구현 검토 기준

1. 사진 선택 뒤 비교용 촬영일 입력 단계를 표시한다. EXIF 확인값이 있으면 미리 채워 보여 주되 사용자가 수정할 수 있어야 한다.
2. EXIF가 없거나 읽는 중이면 촬영일 입력 전에는 업로드·비교 확정을 막고, 이유를 입력 근처에 표시한다.
3. `PhotoRecordUpload`와 비교 전용 업로드 API 모두 `takenAt`을 전달하도록 한 계약으로 맞춘다. 어느 한쪽만 고치면 수상작 상세/사진 놓기 상세 교체 흐름이 다시 실패한다.
4. 서버의 필수 검증은 완화하지 않는다. 클라이언트가 잘못된 요청을 보내도 촬영일 없는 사진 기록이 생성되지 않아야 한다.
