# M8 무한 스크롤 보조 도구 QA 수용 기준

- 작성일: 2026-08-14
- 역할: 통합 QA 사전 검토
- 범위: 수상작 목록(`/contests`)과 키워드 사진 탐색(`/explore`)에 추가할 고정형 `위로 가기`, `다시 검색` 또는 `조건 변경` 보조 도구
- 코드 변경: 없음

## 현재 경계 확인

| 화면 | 목록 상태 | 다음 페이지 조건 | 조건 변경 경계 |
| --- | --- | --- | --- |
| 수상작 목록 | `useContests(query)`의 React Query 무한 목록 | `IntersectionObserver`, rootMargin 200px | `ContestListPage`의 `query` 상태와 `ContestFilterBar` |
| 사진 탐색 | `usePhotos(keyword)`의 React Query 무한 목록 | `IntersectionObserver`, rootMargin 240px | URL `?keyword=`와 `ExplorePage`의 draft/keyword 상태 |

- 보조 도구는 목록 데이터, observer, API 요청을 직접 소유하지 않는다. 페이지 또는 재사용 가능한 프런트 모듈이 스크롤 이동과 조건 편집 진입만 맡는다.
- 수상작의 `조건 변경`은 기존 필터 바에 초점을 이동한다. 현재 조건은 유지한다.
- 사진 탐색의 `다시 검색`은 기존 검색 입력에 초점을 이동하며, 현재 키워드를 지우지 않는다. 사용자가 제출했을 때만 URL과 결과가 바뀐다.

## 수용 기준

### 공통 동작

1. 목록이 첫 화면 높이를 넘겨 실제로 아래로 이동한 뒤에만 보조 도구를 표시한다. 초기 로딩, 빈 결과, 오류 화면, 지도 보기는 표시하지 않는다.
2. `위로 가기`는 `window.scrollTo({ top: 0, behavior: 'smooth' })`를 사용하고, `prefers-reduced-motion: reduce`에서는 즉시 이동한다.
3. `위로 가기` 후 키보드 사용자가 맥락을 잃지 않도록 해당 화면의 제목 또는 주 검색 입력에 프로그래밍 방식으로 포커스를 준다. 포커스 대상에는 보이는 `:focus-visible` 표시가 있어야 한다.
4. 도구는 실제 `<button type="button">`이며 아이콘만 쓸 경우에도 접근 가능한 이름(`aria-label`)을 제공한다. Tab/Shift+Tab/Enter/Space로 모두 동작해야 한다.
5. 고정 도구는 목록의 마지막 카드, 로딩 표시, 빈 상태를 가리지 않는다. 한 화면에 두 개를 둘 경우 하나의 `aria-label`이 있는 그룹 안에 배치하고, 각 버튼의 의미를 텍스트 또는 툴팁으로 알 수 있게 한다.
6. 요청 중(`isFetchingNextPage`)에도 도구는 스크롤 이동과 조건 변경이 가능해야 한다. 단, 조건을 실제로 제출해 새 query key가 생기면 이전 observer가 정리되고 이전 결과가 새 결과에 섞이지 않아야 한다.

### 360px 모바일 및 하단 탭

1. 360px 폭에서 두 버튼의 최소 터치 영역은 각각 44 x 44px 이상이며, 긴 한국어 라벨이 잘리거나 2줄로 찌그러지지 않는다. 필요하면 아이콘+짧은 라벨 또는 확장 메뉴를 사용한다.
2. `BottomTabBar`는 fixed이며 z-index 40, `AppShell`은 모바일 하단 `pb-24`를 이미 사용한다. 보조 도구는 탭보다 위에 떠야 하지만 탭을 덮지 않아야 한다. CSS 위치는 `bottom: calc(env(safe-area-inset-bottom) + 탭 실제 높이 + 여백)`으로 잡고 z-index는 탭보다 높거나, 탭 상단과 명확히 분리되는 낮은 레이어로 검증한다.
3. iOS safe-area가 있는 기기에서도 버튼이 홈 인디케이터나 하단 탭 라벨과 겹치지 않는다.
4. 1/2/3열 선택 토글과 보조 도구가 같은 우측 영역에서 겹치지 않는다. 목록 상단의 열 토글은 스크롤 뒤에도 기존 위치를 유지한다.

### 데스크톱

1. 768px 이상에서 보조 도구는 최대 콘텐츠 폭(`max-w-screen-xl`) 바깥으로 튀어나오지 않고, 세로 스크롤바나 우측 여백을 가리지 않는다.
2. 마우스 휠, 트랙패드, PageUp/PageDown/Home/End 이동 중 보조 도구가 클릭 가능한 위치를 유지한다.
3. 넓은 화면에서도 목록 카드의 hover/click을 가로막지 않으며, 우측 하단 고정 도구가 마지막 행의 상세·좋아요 행동 위를 덮지 않는다.

### observer·로딩·오류 회귀

1. 보조 도구를 열거나 닫고, 위로 이동하고, 필터 입력에 포커스해도 sentinel의 관찰이 중복 등록되지 않는다. 같은 교차 시점에 `fetchNextPage()`가 중복 호출되지 않는다.
2. 마지막 페이지(`hasNextPage === false`)에서는 추가 요청이 발생하지 않으며, 보조 도구만 남아도 빈 sentinel 요청이 생기지 않는다.
3. 다음 페이지 실패 시 기존 결과는 남고 기존 오류 UI 규칙에 맞는 재시도 경로가 제공되어야 한다. 무한 로더만 계속 보이면 안 된다.
4. 조건 변경 직후 이전 목록의 마지막 sentinel이 보이더라도 새 조건의 2페이지를 먼저 요청하지 않는다. 새 첫 페이지가 완료된 뒤에만 observer가 다음 요청을 할 수 있다.
5. React StrictMode 개발 환경에서 effect 재실행에도 observer가 둘 이상 남지 않는다.

### 경로·필터 보존

1. 사진 탐색에서 `?keyword=벚꽃` 상태로 아래까지 내린 후 `다시 검색`을 눌러도 주소와 입력값은 `벚꽃`으로 유지한다. 수정·제출하면 URL과 목록이 함께 바뀐다.
2. 수상작에서 계절·등급·부문·시도·키워드 조건을 둔 상태로 `조건 변경`을 눌러도 query 객체를 초기화하지 않는다. 사용자가 `필터 초기화`를 명시적으로 눌렀을 때만 초기화한다.
3. 수상작 지도 보기에는 무한 목록 보조 도구가 보이지 않는다. 리스트↔지도 전환 시 현재 필터는 유지한다.
4. 브라우저 뒤로가기/앞으로가기 또는 홈·검색 경로 이동 뒤에 이전 화면의 floating 도구가 남아 있지 않다.

## 권고 구현 형태

- `features/.../components/InfiniteScrollAssist.tsx`처럼 표현과 접근성을 한 곳에 두고, 각 화면은 `onScrollTop`, `onRefocusSearch` 같은 의도만 주입한다. 목록·API 훅에 스크롤 UI 규칙을 섞지 않는다.
- 표시 여부를 매 스크롤 이벤트에서 즉시 상태 변경하지 말고, 작은 임계값(예: 320px)과 passive scroll listener 또는 별도 top sentinel 관찰로 계산한다.
- `위로 가기`와 검색/필터 이동은 URL이나 query를 바꾸지 않는 보조 행동으로 유지한다.

## 현재 사전 판정

- 구현 전 차단 이슈: 없음.
- 주의: 하단 탭이 fixed이므로 360px에서 floating 도구의 bottom offset을 실제 탭 높이와 safe-area 기준으로 검증하지 않으면 겹침 회귀 가능성이 높다.
- 주의: 현재 observer는 목록 하단 sentinel에 직접 연결되어 있으므로 검색·필터 포커스/스크롤 처리에서 observer effect 의존성을 훼손하지 않아야 한다.
