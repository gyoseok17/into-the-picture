## 현재 화면·API 기준

| 영역 | 현재 상태 | M8에 주는 의미 |
| --- | --- | --- |
| 시작 화면 | `/`는 `ExplorePage`이며 바로 키워드 검색 결과를 보여 준다. 별도 메인/홈 화면은 없다. | 감성적 진입 화면을 새로 만들려면 홈의 책임을 검색과 분리해야 한다. |
| 탐색 내비게이션 | 수상작, 검색, 혼잡도, 사진 놓기, 마이의 5개 항목을 상단/하단에서 공유한다. | 탐색과 내 기록을 한 레벨에 나열해 정보 우선순위가 약하다. |
| 모바일 | `md` 미만에서 하단 탭만 보인다. 비로그인 사용자는 `마이`가 숨겨진다. | 모바일에서 즉시 로그인으로 가는 명시적 진입점이 없다. 사진첩의 추가/편집 행동도 하단 탭과 겹치지 않게 설계해야 한다. |
| 개인 사진 | `GET/POST/DELETE /me/photos`, 파일 `GET /me/photos/{id}/file`만 있다. 응답에는 `takenAt`, `memo`가 있지만 편집·보관·장소·좌표 API는 없다. | 앨범 목록과 상세의 최소 표시까지는 가능하나, M8의 편집/정렬/지도 기능에는 계약 추가가 필요하다. |
| 사진 비교 | `/me/comparisons`가 사진 기록과 수상작 연결을 제공한다. 교체·연결 해제·사진 삭제를 지원한다. | 사진첩 상세에서 수상작 연결을 표시하고 사진 놓기로 이동하는 기반은 있다. |
| 공통 이미지 | `AspectImage`가 비공개 사진을 인증 API로 Blob 요청해 그린다. | 권한 모델은 유지해야 한다. 지도/그리드에 많은 개인 사진을 동시에 렌더링하면 개별 Blob 요청이 늘어난다. |

## 주요 위험과 판정

### 차단 이슈: M8 사진첩 상세 기능 계약 미정

`PhotoRecord`에는 `placeName`, `archivedAt`, `displayMode` 필드가 이미 있지만, 현재 `UserPhotoDto`와 `/me/photos` API는 이를 충분히 노출·수정하지 않는다. 따라서 아래 기능을 프런트만으로 구현하면 화면 상태와 서버 데이터가 어긋난다.

- 촬영일·장소·메모 수정
- 보관/복원
- 촬영일/장소 정렬·필터
- 개인 사진 지도와 장소별 묶기
- `수상작과 함께 보기` 표시 방식 저장

판정: **M8 메인·공통 레이아웃 작업은 진행 가능. 사진첩의 실제 편집·지도 구현은 백엔드/프런트 계약이 확정되기 전에는 시작 불가.**

### 높은 우선순위 위험

1. **홈과 검색의 책임 혼합** — `/`가 검색 화면이다. 새 메인에 검색 진입을 넣을 경우 검색 결과 상태, 무한 스크롤, 뒤로 가기 상태를 같은 화면에 섞으면 다시 기능 나열형 화면이 된다. `/`는 홈, `/explore`는 검색처럼 라우트를 분리하거나, 최소한 홈과 검색 결과를 명확한 상태 전환으로 분리해야 한다.
2. **개인 사진 대량 로딩** — `AspectImage`는 비공개 사진 한 장당 인증된 Blob 요청을 만든다. 앨범/스토리/지도에서 다수 썸네일을 한 번에 렌더링하면 초기 화면과 스크롤 성능이 떨어질 수 있다. 목록용 썸네일 API 또는 제한된 페이지네이션 계약을 먼저 검토해야 한다.
3. **현재 내비게이션의 과밀** — 모바일 5탭에 모든 기능이 동등하게 보인다. M8에서 `사진첩`을 추가하면서 탭을 더 넣으면 번잡해진다. 사진 놓기는 사진첩 상세의 행동으로도 진입 가능하므로, 메인 탭 유지 여부를 정보 구조 결정으로 기록해야 한다.
4. **삭제 행동의 맥락 부족** — 현재 `MyPage` 사진 카드는 즉시 삭제 버튼을 가진다. 사진첩은 기록 중심 화면이므로 목록에서 위험 행동을 노출하기보다 상세의 수정 메뉴로 모으고, 보관과 영구 삭제를 구분해야 한다.

## 접근성·반응형 점검

- 현재 모달은 `role="dialog"`와 `aria-modal`은 있으나, 포커스 이동/포커스 트랩/닫은 뒤 트리거로 복귀가 없다. M8에서 상세·편집·장소 선택 시트가 늘어나므로 공통 Dialog/Sheet에 이 동작을 갖춰야 한다.
- 닫기 아이콘 버튼 중 일부는 접근 가능한 이름이 없다. 새 공통 패턴은 모든 아이콘 단독 버튼에 `aria-label`을 요구해야 한다.
- `BottomTabBar`는 안전 영역을 고려하고 있으나, `main`의 `pb-24`는 사진첩의 화면 하단 고정 행동(추가/저장)과 이중으로 겹칠 수 있다. 하단 고정 CTA가 있는 화면은 필요한 여백을 화면 단위로 명시한다.
- 현재 데스크톱 상단 메뉴는 `마이`를 닉네임 드롭다운에 숨기고, 모바일은 비로그인 시 로그인 진입이 없다. M8 정보 구조 결정 때 로그인·사진첩 접근 경로를 데스크톱/모바일 각각 검증해야 한다.
- 카드 전체를 버튼으로 쓰는 패턴은 가능하지만, 내부에 별도 버튼/링크가 들어가는 상세 카드에는 중첩 상호작용 요소를 만들지 않아야 한다.

## 조용한 에디토리얼 방향의 구현 권고

1. **페이지 역할을 먼저 고정한다.** 홈은 한 장의 대표 이미지와 탐색 진입만, 검색은 결과 탐색만, 사진첩은 개인 기록만 담당한다.
2. **공통 패턴은 4개로 제한한다.** `SectionHeader`, `PhotoTile`, `RecordMeta`, `EmptyState`만 먼저 만들고 카드·배지·색상 변형을 화면별로 늘리지 않는다.
3. **사진첩의 기본 보기 하나를 먼저 만든다.** 앨범 그리드 또는 시간순 스토리 중 하나를 기본 화면으로 정하고, 지도는 장소 좌표 계약과 빈 상태가 준비된 뒤 추가한다.
4. **행동은 단계적으로 숨긴다.** 사진 탭 → 상세 → 수정 메뉴 순서로 두고, 삭제는 수정 메뉴 안에서만 노출한다. 업로드/저장은 한 화면의 주 행동 하나로 유지한다.
5. **모바일 우선 검증을 고정한다.** 360px 폭에서 탭 수, 이미지 최소 폭, 긴 장소명 두 줄 처리, 모달 스크롤, 하단 CTA 가림을 확인한다.
