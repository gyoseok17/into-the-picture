# M8.3 선택형 사진 저장소 QA·보안 검토

## 1. 사전 계약 검토 (2026-09-17)

- 저장소 선택은 `APP_STORAGE_TYPE`으로 한다. 값이 없거나 `local`이면 기존 `LocalFileStorage`를 사용하고, `s3`일 때만 S3 구현체를 하나 등록한다.
- 두 구현체의 저장 키는 기존 DB 값과 호환되는 `u/{userId}/{uuid}.{extension}`을 유지한다. `user_photo.storage_key`나 사진 제공 API를 이관하지 않는다.
- 사진 응답 URL은 기존의 인증된 백엔드 경로(`/me/photos/{id}/file`)와 공개 비교 전용 경로만 사용한다. S3 객체 URL·presigned URL을 DTO 또는 DB URL에 넣지 않는다.
- S3 선택 시 `AWS_REGION`, `APP_STORAGE_S3_BUCKET`이 누락되면 애매하게 local로 돌아가지 말고 애플리케이션 시작 단계에서 명확히 실패해야 한다.

## 2. IAM 및 버킷 보안 기준

- EC2 역할에는 대상 버킷의 `u/*`에만 `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`를 허용한다. `ListBucket`, `GetObjectVersion`, 버킷 정책/ACL 변경 권한은 현재 기능에 필요 없다.
- 버킷은 Public Access Block을 유지하고 ACL은 사용하지 않는다. 업로드 코드가 `public-read` ACL이나 공개 URL을 요청하면 차단 이슈다.
- AWS SDK 기본 자격 증명 체인을 사용한다. 개발 PC는 AWS CLI/SSO 자격 증명, EC2는 IAM 역할을 쓰며 액세스 키·시크릿을 프로젝트 `.env`, Compose, Git에 추가하지 않는다.

## 3. 데이터 안전성·오류 경로 점검

- 업로드 전 유효성 검사와 EXIF 처리 뒤에 객체를 저장한다. 객체 저장이 실패하면 `UserPhoto`/`PhotoRecord` DB 레코드는 남지 않아야 한다.
- DB 저장 중 실패하면 이미 업로드한 S3 객체를 삭제하는 보상 처리가 필요하다. 보상 삭제 실패는 원본 예외에 억제 예외로 보존하고, 운영 로그에서 고아 객체를 추적할 수 있어야 한다.
- 묶음 업로드 중 일부 실패 시, 이미 저장된 각 객체가 기존 보상 삭제 흐름에서 제거되는지 확인한다.
- 삭제는 현재 서비스 트랜잭션 흐름을 유지한다. S3 삭제 실패를 정상 삭제로 숨기면 DB와 객체가 불일치하므로 실패로 돌려야 한다. S3의 네트워크/권한 예외는 `IOException` 경계로 변환해 기존 서비스의 오류 처리와 호환되어야 한다.
- 기존 local 파일은 자동 이관 범위 밖이다. `APP_STORAGE_TYPE=s3`로 바꾼 뒤 기존 DB 키를 조회하면 같은 키의 S3 객체가 없을 수 있으므로, 운영 전에는 새 데이터만 쓸지 별도 이관할지를 결정해야 한다.

## 4. 구현 도착 뒤 확인할 차단 조건

1. `FileStorage` 빈이 local과 S3로 동시에 두 개 등록되어 의존성 주입이 모호해지지 않는가.
2. `s3` 선택인데 필수 설정이 비었을 때 local로 조용히 대체되지 않는가.
3. S3 `load`가 스트림을 한 번만 읽고, 컨트롤러의 DB 기반 Content-Type/Length 응답과 호환되는가.
4. 객체 키가 사용자 입력 파일명·경로 조작으로 `u/{userId}/` 밖을 벗어나지 않는가.
5. S3 예외가 권한 없는 객체를 공개하거나, 공개 비교 이외 경로에서 객체 URL을 노출하지 않는가.
6. local 기본 모드 및 기존 `LocalFileStorageTest`가 회귀 없이 통과하는가.

## 5. 검증 계획

- 단위: local 기본 선택, s3 선택, 누락된 S3 설정 실패, S3 put/get/delete 호출 키·메타데이터, S3 예외 변환을 테스트한다.
- 회귀: `gradlew.bat test` 전체 실행 후 사진 업로드·묶음 업로드·개인 파일 조회·공개 비교 파일 조회·삭제의 저장소 호출 경계를 교차 확인한다.
- 통합(사용자 PC AWS 자격 증명 준비 후): 비공개 버킷에 실제 upload/load/delete 한 건을 수행하고 AWS 콘솔에서 객체가 `u/` 아래에만 생기며 공개 URL 없이 백엔드 경로로만 조회되는지 확인한다.

## 6. 최종 QA 판정 (2026-09-17)

- 해결(2026-09-17): `S3FileStorageTest`의 AWS SDK `putObject` 오버로드 모호성은 `any(RequestBody.class)`로 수정됐다.
- 해결(2026-09-17): local/S3 간 키 생성·확장자 규칙을 `UserPhotoStorageKey`로 한 곳에 모았고, 알 수 없는 `APP_STORAGE_TYPE`은 `local` 또는 `s3`만 허용하도록 시작 단계에서 실패하게 했다.
- 해결(2026-09-17): 원본 multipart 파일명에서 확장자는 `[a-z0-9]{1,10}`만 사용하고 나머지는 `.jpg`로 대체한다. `x.jpg/../../another-object` 회귀 테스트로 경로 세그먼트·`..`가 키에 들어가지 않음을 확인했다.
- 구현 확인:
  - 조건부 빈으로 `local` 기본 또는 `s3` 구현 중 하나만 `FileStorage`로 등록된다.
  - `s3`는 region/bucket 누락 시 시작을 중단하며 AWS SDK 기본 자격 증명 체인을 사용한다.
  - S3 객체 URL/ACL을 만들지 않고, 개인·공개 비교 파일 모두 기존 백엔드 권한 경로에서 `storageKey`를 읽는다.
  - S3 SDK 예외는 `IOException`으로 변환되어 기존 업로드 보상·조회·삭제 오류 경계와 호환된다.
  - 저장 키와 API/DB 계약은 기존 `u/{userId}/{uuid}.{extension}` 및 서버 파일 API를 유지한다.
- 검증: QA 재실행 `backend\\gradlew.bat test --rerun-tasks` 및 `backend\\gradlew.bat bootJar` 성공. 로컬 기본 모드·S3 mock 단위 테스트·기존 사진/비교 서비스 회귀 테스트가 포함됐다.
- 판정: **통과. 커밋 가능.**
- 남은 운영 검증(차단 아님): 실제 AWS 자격 증명으로 비공개 버킷 upload/load/delete를 한 번 실행하고, 기존 로컬 파일을 S3 모드에서도 보여야 한다면 별도 이관 계획을 세운다.
