# M8.3 로컬 Compose S3 자격 증명 QA·보안 검토

## 검토 범위

- `backend/docker-compose.local.yml`은 Git 제외 로컬 오버라이드이며, base `docker-compose.yml`의 운영 동작을 바꾸지 않는다.
- 오버라이드는 `AWS_PROFILE=into-the-picture-local`과 호스트 `${USERPROFILE}/.aws`의 읽기 전용 bind mount만 추가한다.

## 보안·계약 검토

- Compose 오버라이드·`backend/.env.example`·추적되는 문서에 `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN` 같은 장기 키가 없다.
- `git check-ignore -v backend/docker-compose.local.yml backend/.env`로 두 로컬 파일의 Git 제외를 확인했다.
- 병합 구성에서 AWS 자격 증명은 `/home/appuser/.aws`에 bind mount 하나로만 제공되고 `read_only=true`다. Dockerfile의 실행 사용자가 `appuser`이며 target home과 일치한다.
- 호스트 AWS 설정 파일의 프로필 헤더를 값 노출 없이 확인한 결과, `config`와 `credentials` 모두 `into-the-picture-local` 프로필을 가진다. 이 이름은 오버라이드 및 `_workspace/backend/M8.3-local-compose-s3-report.md`의 사용 방법과 일치한다.
- AWS CLI 자체는 현재 PC에 설치돼 있지 않다. SDK는 mounted shared config/credentials를 직접 읽을 수 있으므로 Compose 구성 차단 사유는 아니지만, CLI로 별도 자격 증명 진단을 하려면 설치 또는 대체 확인이 필요하다.

## 병합 검증

명령:

```powershell
cd backend
docker compose -f docker-compose.yml -f docker-compose.local.yml config --quiet
```

- 성공.
- 병합 후 backend에 `AWS_PROFILE=into-the-picture-local`이 존재한다.
- `/home/appuser/.aws` mount는 `bind`, `read_only=true` 하나다.
- backend는 host `ports`를 추가로 열지 않는다. base의 `/app/uploads` named volume과 Secure refresh-cookie 설정은 그대로다.

## 판정

**통과. 차단 이슈 없음.**

실제 S3 Put/Get/Delete는 다음 단계에서 Docker를 기동한 뒤 수행해야 한다. EC2 운영 배포에는 이 로컬 override를 사용하지 않고 IAM 역할을 사용한다.

## 권고

- 추적되는 `backend/README.md`에는 로컬 Docker S3 테스트용 오버라이드의 생성·실행 방법과 `into-the-picture-local` 프로필명을 간단히 안내하는 편이 재현성이 좋다. 현재 상세 사용법은 Git 제외 로컬 파일과 작업 근거 문서에만 있다.
