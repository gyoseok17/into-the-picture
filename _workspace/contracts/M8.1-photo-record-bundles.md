# M8.1 사진 묶음 계약

작성일: 2026-08-28
상태: 합의 후 구현 중

## 데이터 모델

- `photo_record_bundle`: 사용자 한 명의 한 번의 사진 묶음. 공통 `takenAt`, `placeName`, `mapRegionCode`, `mapCityCode`, `memo`를 보관한다.
- `photo_record.bundle_id`: 선택(nullable) 관계. 기존 사진과 공모전 비교 사진은 `null`을 유지해 개별 기록으로 호환한다.
- 새 다중 업로드는 요청 1회마다 묶음 하나를 만들고, 그 요청의 모든 사진을 같은 `bundle_id`로 저장한다.

## API

- `POST /api/v1/me/photos/bundles`: multipart. `files`(1~3, 파일당 10MB 이하, 요청 전체 32MB 이하), 공통 `takenAt`, `placeName`, `mapRegionCode`, `mapCityCode`, `memo`를 받는다. 응답은 묶음과 내부 사진 목록이다.
- `GET /api/v1/me/photos/bundles?archived=false`: 묶음과 기존 개별 사진을 같은 목록 계약으로 반환한다.
- `DELETE /api/v1/me/photos/bundles/{bundleId}`: 묶음과 내부 사진을 일괄 삭제한다. 비교에 참조된 사진이 하나라도 있으면 409으로 막고 대상은 유지한다.
- 기존 단일 사진 API는 유지한다. 기존 사진은 개별 항목으로 계속 조회·수정·삭제한다.

## 화면 계약

- 스토리: 묶음은 대표 사진, 사진 수, 공통 날짜·장소로 카드 하나를 표시하고 누르면 내부 사진을 확인한다.
- 맵: 같은 묶음은 마커 하나로 표시하고 누르면 내부 사진을 넘긴다.
- 삭제: 관리 모드에서 묶음 또는 개별 사진을 체크한다. 일괄 삭제 전 대상 수를 확인하고, 비교 참조 충돌은 사용자에게 안내한다.

## 안전성

- 파일 저장 실패 시 DB 묶음/사진 레코드가 남지 않도록 트랜잭션·보상 삭제를 적용한다.
- 권한은 모든 묶음 조회·삭제에서 서버 사용자 소유권으로 검사한다.
- 기존 `photo_record` 데이터는 마이그레이션에서 수정·삭제하지 않는다.

## 현재 정책 정정 (2026-09-12)

이 문서의 이전 1~20장 또는 동시 업로드 서술은 초기 계획 기록이다. 현재 구현·운영 계약은 다음으로 대체한다.

- 한 `POST /api/v1/me/photos/bundles` 요청은 사진 1~3장인 하나의 묶음을 만든다.
- 파일 하나는 최대 10MB, multipart 요청 전체는 최대 32MB다.
- 요청은 하나의 묶음을 원자적으로 저장하며, 20장 선택 대기열이나 다중 요청 동시 전송은 제공하지 않는다.

상세 실패 응답은 `M8.1-photo-record-batch-upload-limits.md`를 기준으로 한다.
